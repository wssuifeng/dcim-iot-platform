## 一、背景与动机

单机房链路（虚拟设备 → Modbus TCP → 智能网关 → 北向契约 → 云平台）已稳定运行：
19 台设备 5 类预设、双层环境物理引擎（V2 事件体系）、告警链路常态化触发。

当前瓶颈：**仿真器网关是单例**——

| 现状 | 代码位置 | 多机房后果 |
|------|---------|-----------|
| 网关配置单行（单凭证） | `GatewayConfig`（H2 gateway_config 表无 room 维度） | 一套 AccessKey/Secret 只属于一个机房 |
| GatewayRuntime 轮询全部设备 | `GatewayRuntime.pollAll()` 遍历所有 active 设备 | 多机房设备混在一个上报流里，跨机房凭证上报必然被平台「机房归属校验」拒绝 |
| 平台目录/阈值缓存全局静态 | `GatewayScenarioController.cachedRooms / cachedThresholds`（static volatile） | 多凭证各自拉取时互相覆盖 |
| 管理页单网关表单 | `index.html` 网关与观测 Tab | 无法配置/启停第二个机房 |

平台侧（本仓库）本身已具备多机房模型：机房自带凭证、设备归属机房、告警/统计按机房过滤。
因此本阶段**改造重心在仿真器**，平台只做小量观测增强与压测验收。

## 二、目标

1. **多机房接入**：仿真器支持 N 个网关实例，每个绑定一个平台机房凭证，独立启停、独立轮询与上报；
2. **常态化高负载**：一键构造"中型机房 × N"的稳定态（设备多、上报频率高），可持续运行不劣化；
3. **平台负载能力测试**：在高压下度量平台接收门与告警链路的吞吐/延迟/错误率，产出可复现的压测报告。

### 非目标（明确不做）

- 平台侧不做多租户（单租户三角色已定，见 ADR-001）；
- 不做分布式/多机部署的仿真器集群（单进程多网关足够，见「03-技术设计」§1 的论证）；
- 不引入 JMeter/Gatling 等外部压测框架——仿真器本身就是"官方诚实网关"，负载由它生成（与 ADR-003 精神一致）。

## 三、总体架构决策（摘要，详论证见 03-技术设计）

| # | 决策 | 理由 |
|---|------|------|
| D1 | **网关多实例化**：`gateway_config` 增 `cloud_room_id` + 凭证三元组（平台地址/AccessKey/Secret），一机房一网关 | 与真实机房同构（每机房一台采集网关、一套凭证）；平台契约按机房鉴权 |
| D2 | **设备按 cloud_room_id 分流**：每个网关运行时只轮询/上报本机房设备 | 修复"单凭证上报全部设备"的归属校验必然失败问题 |
| D3 | **平台目录/阈值缓存按房间分片**：`Map<roomId, …>` 替换 static volatile 单值 | 多凭证并发拉取互不覆盖 |
| D4 | **负载由网关侧参数放大**：上报间隔/批量/设备数/机房数四维可调，管理页可预设压测档位 | 负载 = 房间数 × 设备数 × 点均频率，无需改平台 |
| D5 | **平台观测增强仅限只读**：ingest 吞吐计数器（内存滑动窗口）+ 慢请求日志，不改写路径 | 压测要"看得见"，但写路径零侵入，避免观测本身影响压测 |
| D6 | **压测报告以"档位"固化**：每档（如 6 房间 × 20 设备 × 5s 上报）记录吞吐/延迟/错误率/资源 | 可复现、可对比、可回归 |

## 五、验收标准

1. 仿真器管理页可创建 ≥2 个网关（各绑不同机房凭证），独立启停；A 机房网关停止不影响 B 机房数据流；
2. 平台侧两个机房各自出现独立设备清单、独立告警、独立网关观测（last_seen/离线告警）；
3. 常态档（2 机房 × 20 设备）连续运行 ≥1h 无错误日志刷屏、无内存增长、无数据断流；
4. 高压档（具体档位在 04-压测方案定义）下平台接收门无 5xx、幂等去重正常、告警链路不阻塞数据接收；
5. 产出压测报告（05-压测报告模板）：吞吐、P50/P95 延迟、错误率、MySQL/Redis 连接池、JVM 内存，各档位对比表；
6. 平台 `./mvnw test` 全绿；仿真器 `mvn test` 全绿（含新增多网关用例）；
7. 两仓库 README 同步本次能力，文档导览更新。

## 六、风险与边界

- **平台侧连接/线程上限**：N 个网关 = N 条 MQTT 连接 + 心跳 HTTP；压测档位设计时先小后大（见 04）；
- **H2 写入压力**：仿真器自身寄存器刷新 1s × M 设备 × K 指标，寄存器值为内存计算不入库（当前架构即如此），无 H2 瓶颈；北向上报不落仿真器库——仿真器侧无持久化瓶颈；
- **平台 MySQL 写入**：metric_sample 批量插入 + 幂等表是热点，压测重点观察项；TTL 清理任务在高频写入下的表现纳入观察；
- **用户约束**：平台 8081 / 前端 5174 / 仿真器 8090；8080/5173 不可碰；压测产生的数据在报告产出后按用户指示清理（或保留为长期常态数据，由用户决定）；
- **仿真器仓库尚无远程**：推送远程待用户提供地址（本地提交先行）。
