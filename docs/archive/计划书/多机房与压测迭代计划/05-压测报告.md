## 4. 观察项记录

- **样本量模型修正**：变化驱动（死区/越限即报）贡献了绝大部分上报，"上报间隔"更多影响批内条数而非请求数；后续压测若要压请求数，应压小上报间隔（L4 已到 2s 契约下限的合理档）；
- **指标表增速**：L4 下 ~120 行/s，按此速率 24h ≈ 1000 万行——TTL 清理（默认保留期内）在单机房常态档（~1 行/s）下无压力，压测机房如长期保留需关注磁盘与清理滞后；
- **MQTT vs HTTP**：未对比（本轮 6 网关全 HTTP）；MQTT 单连接消费在风暴档的表现留待后续；
- **告警评估**：L4 窗口内机房 113 存在活动 METRIC 告警，评估链路未拖垮接收（失败 0）；
- **定时任务**：网关离线扫描（5min 周期）在高压下无误报（6 网关全部 last_seen 新鲜）。

## 6. 发现与建议（后续迭代候选）

1. **观测直方图改为滑动窗口**：当前累计直方图跨档位混叠（L4 报告里 500ms 槽含 L1 残留），建议滚动 5min 窗口——证据：§2 表；优先级 P2；
2. **存量设备绑定回填机制**：V16/V18 两轮均为"补类型清单 + 手工回填存量"，建议清单同步时对"类型清单扩容"自动补绑（本次靠 V18 迁移兜底）——优先级 P2；
3. **MQTT 通道压测**：单 broker 单连接消费在 L4 下的吞吐未测——P3；
4. **JVM/MySQL 深度观测**：本轮无连续 GC/连接池采样（Windows 主机 + 默认参数），若目标为容量规划需接 Micrometer——P3。

## 7. 结论

- **平台在 L4 风暴档（6 机房 / 105 台 / 120 样本/s / ~4.8 req/s）下满足全部通过判据**：零 5xx、零失败、P95 < 1s、告警与检索功能正常；
- 常态运行推荐：每机房 20 台以内、常态档上报；机房数 ≤6 单机部署无压力（调度池上限 16 网关，理论容量余量充足）；
- 两项 E2E 暴露的真 bug 已修复并合入：网关级告警无法自动恢复（cffe0f7）、PDU_METER 类型指标清单缺口（V18）；
- **数据清理**：压测机房 LOAD-3/4/5/6（机房 113–116）与机房 70 暂保留常态运行作为多机房演示环境，等待用户评审报告后决定清理或转常态化（含告警/采样数据量）。
