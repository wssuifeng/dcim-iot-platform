## 1. 网关多实例化（D1/D2/D3）

### 1.1 数据模型

`gateway_config`（H2，schema.sql 追加列，`ADD COLUMN IF NOT EXISTS` 兼容已有库）：

```sql
ALTER TABLE gateway_config ADD COLUMN IF NOT EXISTS cloud_room_id BIGINT;
```

- `cloud_room_id`：本网关绑定的平台机房 ID。旧单行数据迁移：启动时若存在 `cloud_room_id IS NULL` 的行，取唯一一个有设备的 `room_environment_profile.cloud_room_id` 回填；无法推断则置 -1 并在管理页标红提示重新绑定。
- 其余列不变（name/platform_base_url/ingest_access_key/ingest_secret/传输/轮询/上报/死区/状态）。
- 约束：`cloud_room_id` 业务唯一（不建数据库唯一索引，因 NULL 兼容期；Service 层校验"一机房一网关"）。

### 1.2 运行时结构

现状：`GatewayRuntime` 单例持有一个 `NorthboundClient`、全局 `latestValues/lastReported/offlineStreak/cachedThresholds`。

改造（类均在 `com.dcim.simulator.gateway`）：

```
GatewayInstance        ← 新建：单网关的全部运行态
  ├ GatewayConfig config                // 所属配置（含 cloudRoomId）
  ├ NorthboundClient client             // 本网关独立北向连接
  ├ Map<String, Map<String, BigDecimal>> latestValues   // 仅本机房设备
  ├ Map<String, BigDecimal> lastReported
  ├ Map<String, Integer> offlineStreak
  ├ Map<String, List<Threshold>> thresholds   // 本机房阈值（本地越限即报用）
  ├ LocalDateTime lastPoll / lastPeriodicReportAt / lastAlarmReportAt / lastHeartbeatAt
  └ pollOnce() / reportOnce() / heartbeatOnce()   // 从 GatewayRuntime 原方法平移

GatewayRuntime（改造为注册表 + 调度器，保持类名避免大范围改注入）
  ├ Map<Long, GatewayInstance> running   // configId → instance
  ├ start(config) / stop(configId) / reload(config)
  ├ @Scheduled(fixedDelay=1000) tick()   // 遍历 running，按各自周期执行 poll/report/heartbeat
  └ snapshotOf(configId) / offlineOf(configId)   // 观测按网关取
```

关键行为：

- **设备分流（D2）**：`pollOnce` 的设备来源从 `findByStatusOrderById(0)` 改为按 `cloud_room_id` 过滤（新增 repository 方法 `findByStatusAndCloudRoomIdOrderById`；设备量上万时内存过滤也是兜底可行，但直接走 JPA 派生查询）。
- **轮询并发**：单 tick 内多网关串行轮询会随网关数线性拉长节拍。改造为每网关一个独立单线程调度（`ScheduledExecutorService`，池大小 = 网关数上限 16），网关间互不阻塞；同网关内设备仍串行（与真实网关一致）。
- **心跳独立**：每实例 30s 一次，互不影响；A 网关停止即其心跳停发 → 平台侧该机房网关离线告警按既有链路触发，B 网关不受影响。
- **`@PreDestroy`** 关闭全部 client 与线程池。

### 1.3 平台缓存分片（D3）

`GatewayScenarioController` 的 `cachedRooms/cachedThresholds` static volatile 移除：

- 阈值缓存移入 `GatewayInstance.thresholds`（每网关自己拉自己的）；
- 机房目录缓存保留全局一份（单租户平台全量房间列表对所有凭证可见，来源任一凭证的 export 均一致），但存放位置移到独立的 `PlatformDirectoryCache` 组件（去掉 static，正常 bean）；
- `sync-thresholds` / `sync-inventory` / `ping` 端点全部增加 `gatewayId` 参数（旧无参调用保留兼容：作用于第一个网关）。

### 1.4 REST 契约变更（/api/sim）

| 端点 | 变更 |
|------|------|
| `GET /gateways` | 新增：网关列表（含 cloudRoomId、运行状态、设备数统计） |
| `POST /gateways` | 新增：创建（cloudRoomId 必填 + 凭证三元组 + 轮询/上报参数） |
| `PUT /gateways/{id}` | 新增：编辑后热重载 |
| `DELETE /gateways/{id}` | 新增：删除前须先停止 |
| `POST /gateways/{id}/start` \| `/stop` | 新增：独立启停 |
| `GET /gateway` | 保留：返回第一个网关（前端过渡期兼容，S2 完成后前端不再调用） |
| `POST /gateway` | 保留同上语义 |
| `POST /platform/sync-thresholds?gatewayId=` | 增参；无 gatewayId 时作用于第一个 |
| `POST /platform/sync-inventory?gatewayId=` | 增参；清单只含该网关机房设备（现状是全量设备，多机房下必然归属失败——**顺带修复**） |
| `POST /platform/ping` | 不变（请求体自带凭证三元组） |
| `GET /platform/rooms` | 不变（数据源换 PlatformDirectoryCache） |

### 1.5 兼容与迁移

- 存量单网关环境（当前 19 台设备单机房）：启动自动回填 `cloud_room_id`，行为不变；
- `SimulatorLifecycleService.reloadGateway(config)` 改为走注册表 reload；
- 剧本播放器（ScenarioPlayer）注入的 GatewayRuntime 引用不变，接口签名兼容则零改动。

## 2. 批量设备工厂（S2）

新增 `POST /api/sim/rooms/{cloudRoomId}/device-suite`：

```json
{
  "tempHumidity": 8, "ups": 2, "pduMeter": 4, "precisionAc": 3, "leakDetector": 2,
  "codePrefix": "DC1", "seed": 42
}
```

行为：

- 逐台创建虚拟设备：deviceCode = `{prefix}-{类型缩写}{序号}`（如 `DC1-TH03`），typeId 取预设目录，modbus 端口从 15000 起顺序分配（查询当前最大端口 +1），presetId 通道/寄存器初始化复用现有 `createDevice` 逻辑；
- 自动创建该机房环境档案（不存在时）——复用 `createProfile`，种子可指定；
- 幂等：deviceCode 冲突则该台跳过并在响应中报告，不中断整批；
- 响应：`{created: n, skipped: [{deviceCode, reason}]}`。

## 3. 负载放大模型（D4）

负载公式（平台视角每分钟样本量）：

```
samples/min = Σ(网关) 设备数 × 点数/设备 × 60 / reportIntervalSec
            + 死区/越限额外上报（估计 ≤ 20%，物理引擎驱动下温度等模拟量常触发死区）
```

档位参数（每网关可独立设置，管理页提供预设按钮）：

| 档位 | reportIntervalSec | pollIntervalSec | 说明 |
|------|------------------|-----------------|------|
| 常态 | 60 | 5 | 现状默认 |
| 高频 | 10 | 2 | 单机房自身加密 |
| 风暴 | 2 | 1 | 压测上限档；配合批量上报逼近平台 200 条/批契约上限 |

- 上报批量：`maybeReport` 现为一次 `client.report(items)` 全量发。平台契约单批 ≤200 条，改造为**分片发送**（200/批），既是契约合规也是压测可调参数；
- **客户端指标（D4 关键产出）**：`NorthboundClient` 增加内建统计——请求计数、成功/失败、最近 256 次 HTTP 往返延迟（环形缓冲），`GET /api/sim/load-stats` 按 网关 聚合输出（qps/p95/错误率），压测报告的客户端侧数据源，平台侧对应 §4。

## 4. 平台观测增强（D5，iot-platform-main）

只读计数器，零写路径侵入（计数用 `LongAdder`，直方图用固定槽位数组，无锁竞争热点）：

- 新组件 `ingest/IngestMetricsCollector`（@Component）：
  - 计数：batchesIn / samplesAccepted / samplesRejected(按 ResultCode 细分) / samplesDeduped / autoRegistered，HTTP 与 MQTT 分别计；
  - 延迟：每批处理耗时（接收→处理完成）固定槽直方图（1/5/10/25/50/100/250/500/1000ms+）；
- 采集点：`IngestCore`（传输无关核心）批处理首尾各一行，异常路径计数；
- 暴露：`GET /api/observability/ingest-metrics`（ADMIN/OPERATOR 可读，返回 JSON 快照 + `since` 时间戳，供压测脚本轮询）；
- 慢请求日志：批次处理 >200ms 时 WARN 一条（含 TraceId、条数、耗时），压测时日志可见毛刺；
- **不做**：不接 Micrometer/Prometheus（引依赖超出必要；JSON 端点足够本次压测）。

## 5. 平台侧已知热点（压测观察项，不改代码除非压测暴露问题）

- `metric_sample` 批量插入与索引膨胀（`device_code+point_code+sample_time`）——TTL 清理任务在高写入量下的滞后；
- `ingest_dedup` 幂等键写入与清理节奏；
- 告警评估同步链（每样本事务内）在高频下的放大；
- MQTT 适配器单连接消费是否成为吞吐瓶颈（风暴档预期观察项）。

压测若暴露上述瓶颈，修复属于**后续独立迭代**（记入压测报告"发现与建议"），不在本阶段范围。

## 7. 风险对策

| 风险 | 对策 |
|------|------|
| 多网关线程池上限 | 池上限 16；超过即拒绝创建并提示（16 机房 × 20 设备已超风暴档需求） |
| H2 schema.sql 旧库列缺失 | 沿用 `ADD COLUMN IF NOT EXISTS` 模式（V1 物理引擎已验证） |
| 前端单网关表单迁移期断链 | 保留 `GET/POST /gateway` 兼容端点直到 S2 完成 |
| 压测数据污染常态环境 | 压测机房独立命名（`LOAD-{n}`），报告后按用户决定清理或保留 |
| 平台 Redis/MySQL 连接池耗尽 | 风暴档前先跑高频档观察 Druid 指标，逐档升压（见 04-压测方案） |
