# ADR-006: 首包自动注册与设备类型智能匹配

> 状态：已采纳（2026-08-27 定稿，2026-08-28 落地，提交 e26f795 / 3af8192）
> 关联：ADR-005（机房即接入主体）、V13 迁移

## 背景与问题

现实动环工程是"两次录入"：网关侧配南向点表，平台侧再手工/Excel 建设备清单。阶段二最初实现沿袭了这一形态——平台设备纯手工建，ingest 收到未知 deviceCode 即拒绝，联调时需要在平台与仿真器各录一遍。另有一个隐藏缺陷：设备删除为逻辑删除，device_code 唯一索引被墓碑行占坑，同码设备永远无法重建。

## 决策

1. **首包自动注册为主**：凭证维度 `auto_register` 开关（默认开）。收到未知 deviceCode 即自动建档（挂凭证所属机房、名称回退编码、在线状态），并从类型点位模板复制绑定，开箱即收数。失败降级为该条 failed，不阻塞同批其他条目。
2. **类型三级解析**：清单显式 `deviceTypeCode` > 上报点位编码前缀推断（temp/hum→温湿度，voltage/current→UPS，power→电表，leak→漏水）> 凭证默认类型兜底。凭证默认类型从必填降级为可选。
3. **清单上报为辅**：`POST /ingest/inventory` 显式导入（已存在设备补建缺失点位绑定），凭证未开自动注册时返回 unknown 比对清单供人工导入。
4. **物理身份语义**：设备编码是网关世界的物理身份——`findByCode` 无视逻辑删除位；自动注册命中墓碑行时复活并改挂当前机房/类型，而非撞唯一键失败。
5. **编码防重**：`GET /devices/code-available` 供前端添加设备时实时校验。

## 后果

- 正面：接入从"两次录入"收敛为"网关自己说清楚"；多类型机房不再依赖"一机房一类型"的隐含假设；删错设备可重建。
- 负面/约束：自动注册对恶意网关是"写放大"入口（受 Gateway 签名与机房归属校验约束，风险可接受）；类型推断表是硬编码映射，新设备类型需改代码（后续可配置化）。
- 待办关联：告警点位模版重构（`docs/点位模版重构与前端UI重设计计划.md` 第一部分）落地后，自动注册设备的告警规则跟随将从"模板项动态解析"改为"类型基础模版"，语义更直观。

## 替代方案（已否决）

- **纯人工审核（清单落待审核状态）**：适合多租户 SaaS，自部署单租户场景是过度设计。
- **仅清单导入，不做首包注册**：保留两次录入，被用户否决。
