## 一、IM webhook 告警渠道测试（S8-2，核心手动项）

### 前置条件

- 平台运行中（8081），以 ADMIN 登录前端（5174）；
- 侧栏「告警通道」页可用（仅 ADMIN 可见）。

### 1.1 企业微信群机器人

1. PC 端企业微信 → 目标群 → 右键群设置 → 群机器人 → 添加 → 创建新机器人，任意命名（如 "dcim 告警"）；
2. 复制 webhook 地址（形如 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx`）；
3. 平台「告警通道」→ 新增渠道：名称`运维群-企微`、类型`企业微信群机器人`、粘贴地址、凭证 JSON 留空、最高推送级别选 `L3 及以上`、启用；
4. 点「测试发送」。

**预期**：群内几秒内收到 `[测试] dcim 告警通道连通性测试` 消息；页面提示测试成功（含响应摘要）。

### 1.2 钉钉（注意生态现状）

> 钉钉 2023-09 起已停止创建新自定义机器人。若你钉钉里还能添加（存量入口），按下述步骤；**新接入建议走"企业内部应用机器人"**（钉钉开放平台建企业内部应用 → 机器人 → 获取 `/robot/send?access_token=` 地址，报文与加签方案与渲染器兼容）。

1. 钉钉群 → 设置 → 智能群助手 → 添加机器人 → 自定义（如可见）；
2. 安全设置**必须三选一**：
   - 选「加签」→ 复制 SEC 开头的 secret；
   - 选「自定义关键词」→ 建议填 `告警`（平台消息文案含"告警"字样即可命中）；
   - IP 白名单不推荐（出口 IP 不固定）；
3. 平台新增渠道：类型`钉钉`、粘贴地址；选了加签则凭证 JSON 填 `{"secret":"SECxxx"}`，关键词方式则留空；
4. 测试发送。

**预期**：群内收到测试消息。若收到但提示 errcode≠0 相关错误 → 检查关键词/secret 配置（页面会显示具体错误原因）。

### 1.3 飞书

1. 飞书群 → 设置 → 群机器人 → 添加机器人 → 自定义机器人；
2. 安全设置选「签名校验」→ 复制密钥；
3. 平台新增渠道：类型`飞书`、粘贴地址、凭证 JSON 填 `{"secret":"复制的密钥"}`；
4. 测试发送。

**预期**：群内收到测试消息（签名在请求体内，时间戳秒级，均为代码已实现口径）。

### 1.4 ntfy（可选，最简单的开荒渠道）

1. 浏览器开 https://ntfy.sh ，输入自定义主题名（如 `dcim-myroom-alerts`）并订阅；
2. 平台新增渠道：类型`ntfy`、地址 `https://ntfy.sh/dcim-myroom-alerts`、凭证留空；
3. 测试发送。

**预期**：ntfy 页面/手机 App 收到推送，标题形如 `dcim 告警 L3`，紧急级别告警优先级更高（手机会响铃）。

### 1.5 Telegram（可选）

1. Telegram 里找 @BotFather → `/newbot` 建机器人 → 拿到 bot token；
2. 给自己的 bot 发一条 `/start`；
3. 访问 `https://api.telegram.org/bot<TOKEN>/getUpdates` 拿到 chat_id（数字）；
4. 平台新增渠道：类型`Telegram`、地址 `https://api.telegram.org/bot<TOKEN>/sendMessage`、凭证 JSON 填 `{"chat_id":"你的数字ID"}`；
5. 测试发送。

**预期**：Telegram 收到消息；凭证漏填 chat_id 时保存后被明确报错提示。

### 1.6 失败重试与真实告警链路（所有渠道通用）

1. 新增一个故意不可达的渠道（地址 `https://127.0.0.1:9/hook`），启用；
2. 用仿真器制造一条真实告警（如温度演练）；
3. 检查告警通知日志（告警详情/通知日志查询）。

**预期**：
- 真实渠道收到告警（文案含级别标签、事件类型、规则明细）；
- 不可达渠道出现 4 条失败记录（1s/5s/30s 退避共 4 次尝试），`最终失败`字样；
- 可达渠道不受坏渠道影响；告警恢复后再收到一条 ALARM_RECOVERED 推送；
- 平台整体无卡顿（重试在后台线程）。

### 1.7 级别过滤边界

1. 某渠道最高推送级别设为 `L2 及以上`；
2. 制造一条 L3 告警（一般级别）。

**预期**：该渠道**不推送**（L3 数字大于 2，低于紧急度门槛），站内通知正常——过滤公式是 `alarm_level ≤ max_alarm_level`（数字小=严重）。

## 二、告警三机制演练（S8-1，配合仿真器）

> 操作入口：告警模版编辑器 → 规则行「编辑」→ 勾选「配置高级机制」。所有机制**默认不启用**，存量行为零变化。

### 2.1 连续越限（M1）

1. 选温湿度类型基础模版的温度规则行，设「连续越限」= 3，保存；
2. 仿真器环境演练：让温度缓慢爬升越过阈值（如高温阈值 35℃）；
3. 观察告警列表。

**预期**：第 1、2 个越限采样点**不告警**；第 3 个连续越限点到达时触发，文案含 `连续3个采样点越限`；中途温度回落进安全区会清零计数（再爬升需重新数满 3 点）。

### 2.2 变化量急变（M2）

1. 规则行设「变化量限值」= 5、「变化量窗口」= 60 秒；
2. 仿真器演练「火灾热注入」（环境演练按钮，温度会跳变）。

**预期**：即使温度还没过 35℃ 阈值，60 秒内变化超过 5℃ 立即触发，文案含 `疑似急变`。

### 2.3 恢复静默窗口（防抖）

1. 保持告警活动中，让温度在阈值附近来回振荡（演练注入/撤销交替）；
2. 观察告警事件数量。

**预期**：振荡不产生反复的"触发→恢复→再触发"事件（恢复要求 300 秒窗口内无越限采样）；告警事件数 = 真实物理事件数。

### 2.4 再告警（M3）

1. 规则行设「再告警间隔」= 1800 秒，制造持续越限并保持不恢复；
2. 观察 30 分钟后站内通知。

**预期**：同一告警事件约 30 分钟后重发通知，站内标题为 `告警持续未恢复`，不新建事件、不升级级别。

### 2.5 恢复迟滞（hysteresis）

1. 规则行设「恢复迟滞」= 1.5（GT 35 规则 → 安全区为 < 33.5）；
2. 让温度回落到 34.5（不越限但未进安全区）。

**预期**：告警**不恢复**（死区）；继续降到 33.5 以下才恢复。

## 三、TB 兼容遥测 API（S8-10）

1. ADMIN → 机房管理 → 目标机房 → 「签发/重置 TB 遥测 token」，绑定默认设备编码（如 `tb-dev-01`），复制返回的 token（仅显示一次）；
2. curl 上报（简单对象格式）：

```bash
curl -X POST "http://localhost:8081/api/v1/<TOKEN>/telemetry" \
  -H "Content-Type: application/json" \
  -d '{"temperature": 22.5, "humidity": 60}'
```

3. 同样内容再发一次；再试 TB 时间戳格式 `{"ts":<毫秒>,"values":{"temperature":25}}` 与数组格式。

**预期**：
- 第一次：设备 `tb-dev-01` 自动注册并入库（自动注册开启时），机房归属正确；
- 重复发送：不重复入库（无 seq 幂等按 sampleTime 降级）；
- 错误 token：返回 401；报文不带 device 且未绑默认设备：返回 422。

## 四、MQTT 子凭证真机直连（S8-5，需要真实 ESPHome/存量设备时）

1. ADMIN → 机房 → 「签发 MQTT 子凭证」，复制用户名/密码（仅显示一次）；
2. broker 侧配置连接层鉴权（mosquitto 需启用 dynamic-security 并创建对应用户，或 `ingest.mqtt.broker-auth=mosquitto-dynsec` 让平台自动供给）；
3. ESPHome 配置 mqtt broker 地址 + 该用户名/密码，发布平台格式 batch JSON 到 `dcim-open/<用户名>/samples`；
4. 故意用错误密码连接。

**预期**：正确凭证数据入库且归属该机房；错误密码被 **broker** 拒绝（连接层就进不来）；标准 HMAC 通道网关不受影响（两通道共存）。

> 开发侧已用 mosquitto 容器完成平台链路验证（归属/幂等/自动注册全通过），此项只剩真实设备身份的端到端体验确认。

## 六、用于测试仿真服务的第三方工具矩阵（现状与计划）

| 工具 | 用途 | 状态 |
|------|------|------|
| **pymodbus** | 南向：真实 master 读仿真 slave（值比对/异常码/流同步/长连接） | ✅ 已完成，脚本 `scripts/verify_southbound_modbus.py` 归档，可重放 |
| **Node-RED**（node-red-contrib-modbus） | 南向：第三方网关周期轮询 + 北向流（签名/首包注册） | ✅ 已完成，flow JSON 归档，验收可复用 |
| **mosquitto_pub/sub** | 北向：MQTT HMAC 通道 + 开放通道真机验证 | ✅ 已完成（2026-08-31，双通道通过） |
| **Diagslave / ModbusPal** | 交叉对拍：它们的 master 读我们 slave；我们网关读它们 slave | ⏳ 按需手动跑（改动南向协议/解码时才需要） |
| **ThingsBoard IoT Gateway** | 北向：TB 生态网关按 token 上报（对打 S8-10） | 🆕 建议纳入下轮：装一个 TB 网关实例把 Modbus 设备数上报到平台 token，作为 S8-10 的生态级验收 |
| Telegraf | 北向：无签名 HTTP 输出 | ❌ 评估后不做（需破坏签名安全边界，S8-10 已用 token 通道覆盖同需求） |
| 主流 IM 机器人（本文档 §一） | 通知链路 | 🆕 本文档（你手动创建机器人） |

> 结论：**测试仿真服务的工具链已基本打满**（pymodbus/Node-RED/mosquitto 均已实测并归档可重放），计划新拉的只有 ThingsBoard 网关实例（验证 S8-10 token 通道在真实 TB 生态下工作）与 Diagslave 交叉对拍（改协议时才需要）。
