# 01 · 阶段八开发计划（真实用户打磨）

> 定位锚点：面向"管 1~6 个机房的小团队运维"，做到三句话——**告警一定送到、设备半天接完、不骚扰人**。
> 证据底座见 00-调研问题总账与开源项目清单.md；测试与验证安排见 02-测试与验证计划.md。
> 端口约定：平台 8081 / 前端 5174 / 仿真器 8090；每任务卡独立提交。
> 版本：v2（2026-08-30 按用户评审意见重构——S8-1 三机制、S8-2 官方文档为准、S8-3 延后、S8-5 MQTT 子凭证、S8-6 前置事实调研；S8-7~S8-10 已批准执行）。

## 〇、前置事实（评审确认的设计前提）

1. **设备异常 ≠ 停止上报**：真实网关在设备"值异常"时依然按常规心跳/上报频率推数；只有连接断开才停报，断连由 OFFLINE 规则与网关离线链路兜底。因此基于采样流的告警机制均成立，稀疏采样（长心跳）是唯一需要设计照顾的变量。
2. **正常心跳/上报周期量级**：仿真器默认轮询 5s / 上报 60s；真实网关常见 30s~5min。一切"次数/时间"类机制必须对两种量级都成立。

## 一、任务卡

### S8-1 告警规则增强：三机制 + 一补充（P0，对应 G1/G7）

规则行（alarm_template_item）新增四个可选配置，**全部默认不启用**（存量模版行为零变化）：

| 机制 | 字段 | 语义 | 触发行为 |
|------|------|------|---------|
| M1 连续越限 | `breach_count INT DEFAULT 0` | 连续 N 个采样点越限（"心跳次数内未恢复"）——计数与心跳频率解耦的次数口径 | 第 N 个越限点到达即告警；中途回落进迟滞安全区则清零 |
| M2 变化率 | `rate_limit DECIMAL(18,4) DEFAULT NULL` + `rate_window_sec INT DEFAULT 60` | 窗口内 |Δvalue|/Δt 超过限值（如 5℃/min）→ 疑似火灾/急变 | **直接告警**（不等阈值、不等持续） |
| M3 再告警 | `re_alarm_sec INT DEFAULT 0` | 活动告警未恢复且持续越限超过恢复时间阈值 | 重发通知（同一告警事件，升级语义），避免"一直响"与"持续异常沉默"两头的疲劳 |
| 补充 | `hysteresis DECIMAL(18,4) DEFAULT 0`（保留） | 恢复裕度 | 恢复判定要求回落到 `threshold ± hysteresis` 安全区，防阈值附近振荡 |

**配套状态模型**（V19）：

- 新表 `alarm_condition_state`（rule_item_id, device_id, first_breach_at, breach_count, last_value, last_time，唯一键 rule_item_id+device_id）：M1 的连续计数与首越限时刻持久化，重启不丢；
- 防抖合并：恢复后 `quiet_window_sec`（默认 300s，全局配置）内再次越限视为同一事件延续（状态迁移记 FLAP_MERGED，不新建告警事件）；
- M2 依赖最近采样（metric_latest 值 + 采样时间），Δt ≤ 0 或样本不足时**跳过该机制**（回退直接阈值判定）。

**长趋势判断（评审问题的设计回应）**：采纳兜底原则"趋势不成立→直接执行"。本阶段 M2 变化率即趋势异常的一阶近似（最近两点斜率），天然适配稀疏采样；完整的基线学习型长趋势（滑动窗口斜率/均值漂移 + 置信守卫）列为 P2 扩展（S8-1b），实现时同样内建"样本不足→回退直接阈值"语义。

**配套改动**：阈值导出接口透出新字段（网关侧仅透传展示，判定仍在平台）；前端规则行编辑器加四字段；V17 基础模版默认值策略：温度类 M1=3 次，漏水/离线保持立即。

**测试**：M1 计数/中途回落清零/M3 再告警/M2 变化率（正例+样本不足回退）/防抖合并/重启续算/存量零影响，≥10 例。

### S8-2 告警通知渠道：IM webhook 兼容 + 前端配置界面（P0，对应 G2）

**通道现状**：站内铃铛、WebSocket 弹窗、邮件三通道保留不动（注：弹窗本质也是站内形态；实体通道如短信/电话依赖第三方平台能力，属后续专项）。

**新增**：

- 新表 `alarm_webhook_channel`（id, name, channel_type: WECOM/DINGTALK/FEISHU/NTFY/TELEGRAM/GENERIC, webhook_url, credential_json（各平台所需 key/secret/加签配置，结构按渠道文档定义）, min_level, enabled）；
- **凭证与配置全部数据驱动、不写死**：报文模板与加签算法按 channel_type 实现，但 URL、密钥、关键词/secret 等一律来自配置；前端新增"告警通道配置"管理界面（CRUD + 启停 + **测试发送**按钮）；
- **实现纪律：以各平台官方最新文档为准**（钉钉自定义机器人、企业微信群机器人、飞书自定义机器人 webhook 的加签/关键词/频率限制等），实现前逐家核对官方文档并在此任务卡记录文档链接与版本日期，禁止凭印象编造报文格式；
- 分发链在站内/邮件之外并行挂 webhook 分发器，失败退避重试 3 次，结果入 `alarm_notification_log`（channel 字段区分）；
- 与 S8-1 的 M3 再告警共用"同一事件重复通知"的日志口径。

**用户侧前置**：用户后续到各平台创建机器人并获取 key（届时填入配置界面即可，代码先行联调用本地 stub）。

**测试**：各渠道报文渲染（以官方文档样例为断言基准）、失败重试、min_level 过滤、配置 CRUD，≥8 例。

### S8-3 告警通道静默检测 / watchdog（**延后**，对应 G3）

评审决定**本阶段延后**：实体告警通道（短信/电话/语音）尚未接入，静默检测的通知出口仍是站内/邮件（与机房同网同电源时无带外价值）。待 S8-2 渠道跑通、且后续接入第三方实体通知平台后，连同"带外告警部署指引"一并实施。G3 的证据与方案保留在 00 总账，状态改为"延后（依赖实体通知通道）"。

### S8-4 采样数据分区与降采样（P1，对应 G4/G10，**已批准**）

维持原方案：V20 按 `sample_time` 月分区 + `metric_sample_hourly` 聚合表，趋势端点按跨度自动路由（≤48h 原始 / >48h 聚合），观测直方图改滑动 5 分钟窗口。

**已知缺陷与长期优化备忘（记入本卡，交付时同步进 README）**：

- 分区键必须在唯一键内（MySQL 限制）：主键需调整为 (id, sample_time) 组合，影响点需回归；
- 分区粒度=月：TTL 精度下降，保留"drop 分区 + 行级删除"混合清理；
- 当前小时不入聚合表，聚合表存在 ≤1h 滞后；
- **长期演进**：样本量进入千万级/日或趋势查询仍不达标时，评估迁移时序数据库（TDengine / Apache IoTDB / TimescaleDB / VictoriaMetrics 四选型对比），迁移前提是 ingest 写路径抽象已隔离存储层——本阶段顺带校验该抽象。

**测试**：聚合正确性/边界小时/趋势路由/分区裁剪 EXPLAIN，≥6 例。

### S8-5 MQTT 子凭证：存量生态直连接入（P1，对应 G5，**按评审设计执行**）

**问题**：MQTT Ingest 契约要求报文内嵌 HMAC 签名，ESPHome/NUT/HA 等开源生态组件均不支持，存量硬件无法接入。

**方案（评审定稿）**：

- 现有机房凭证体系（AccessKey/SecretKey）基础上，增加 **MQTT 专用子凭证**：每个机房可生成一组独立的 **MQTT 用户名/密码**，与机房 ID 绑定，支持重置；
- 该凭证**仅用于 MQTT 连接层鉴权，不参与 HMAC 签名逻辑**；
- 设备端使用该用户名/密码连接后，平台自动识别归属机房，该连接上报的所有数据归属该机房；
- **标准 HMAC 接口保持不变**，作为标准网关的认证路径，两者共存互不影响；
- 开放通道与签名通道使用不同 topic 命名空间（签名：`dcim/{accessKey}/…`；开放：`dcim-open/{mqttUsername}/…`），机房归属由"username↔topic 前缀一致性 + 凭证映射"双重校验。

**实现要点**：broker 侧鉴权采用 mosquitto dynamic-security（平台管理账号动态增删 MQTT 用户），避免 passwd 文件手工维护；平台 MQTT listener 增开放命名空间订阅，报文直入传输无关核心（机房归属来自凭证映射）；速率限制与最小权限按开放通道口径设计。

**网安**：开放通道纳入后期**专项网安工作**（渗透测试、漏洞挖掘与响应、加固建设），本阶段按最小权限实现并在代码注释标注安全审查点。

**测试**：子凭证 CRUD/重置、错误密码拒绝、username-topic 一致性校验、开放通道入库 + 归属机房正确、HMAC 通道回归不受影响，≥6 例。

**验收**：mosquitto + ESPHome 模拟发布器用子凭证直连，数据入库归属正确机房。

### S8-6 设备接入形态前置事实调研（P1，对应 G6，**先调研后设计，本阶段不实现预设**）

评审指出：在定义"常见设备预设"之前，必须先区分**设备如何接入云平台**的前置事实。本任务卡改为调研产出：

1. 接入形态分类与取证：
   - 形态 A：普通裸设备（RS485/Modbus RTU）→ **经采集网关**协议转换后北向上报；
   - 形态 B：智能网关（自带多协议驱动，Modbus/SNMP/BACnet…）→ 同 A 但网关智能化；
   - 形态 C：具备独立联网能力的设备（IP 接入，自带 HTTP/MQTT 客户端）→ **自己上报自己的数据**，无需网关；
2. 三种形态各自的：凭证形态（机房 AK/SK vs 子凭证）、上报路径（ingest 两条通道均可）、平台侧建模差异（设备档案由谁建、类型推断是否适用）、典型真实器件举例；
3. 产出：前置事实文档（ADR-008 候选），明确寄存器库（原 S8-6 预设）适用于形态 A/B、形态 C 走 S8-5 类直连——**预设功能与寄存器库随 ADR 结论另行排期**。

## 二、实施顺序（v2）

```
第一批（P0 + 护栏）：S8-1 规则三机制 ──► S8-2 webhook 渠道（M3 再告警共用日志口径）
                     S8-7 CI ──► S8-8 前端测试（尽早建护栏）
第二批：S8-4 分区聚合（完成后复跑 L4 压测对比）
         S8-9 下行 webhook ──► S8-10 TB 兼容 API（ADR-008）
第三批：S8-5 MQTT 子凭证（ESPHome/NUT 直连演示）
         S8-6 接入形态前置调研（产出 ADR 素材，预设另行排期）
延后：S8-3 watchdog（依赖实体通知通道，待渠道跑通后随带外指引一并做）
```

## 三、阶段验收（对照 01 目标）

1. 30 天稳定线：误报告警（非演练、10 分钟内自恢复）占比 <10%（依赖 S8-1 三机制生效）；
2. 送达线：告警经站内 + 至少一家 IM webhook 双通道到达（真实机器人），失败可见重试日志；
3. 兼容线：ESPHome/NUT 模拟发布器经 MQTT 子凭证直连入库、归属正确；HMAC 通道回归全绿；
4. 规模线：30 天趋势 <3s + L4 复跑对比 + 容量规格上 README（含时序库长期演进备忘）；
5. CI 全绿 + 前端 ≥10 例；
6. ADR-008（接入形态 + TB 兼容边界）产出。
