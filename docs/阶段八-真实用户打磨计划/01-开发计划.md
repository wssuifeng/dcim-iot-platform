# 01 · 阶段八开发计划（真实用户打磨）

> 定位锚点：面向"管 1~6 个机房的小团队运维"，做到三句话——**告警一定送到、设备半天接完、不骚扰人**。
> 证据底座见 00-调研问题总账与开源项目清单.md；测试与验证安排见 02-测试与验证计划.md。
> 端口约定：平台 8081 / 前端 5174 / 仿真器 8090；每任务卡独立提交。

## 一、阶段目标（可验证）

1. **30 天稳定线**：常态多机房（≥2 机房 30 台）连续运行 30 天，误报告警（触发后 10 分钟内自恢复且非演练）占比 < 10%；
2. **送达线**：任一告警产生后，能通过 ≥2 条独立通道（站内 + webhook）到达；未确认告警按策略升级；
3. **接入线**：常见真实设备（≥2 款主流型号）从选型到出数 ≤ 30 分钟；ESPHome/NUT 桥接 payload 可入库；
4. **规模线**：README 写明容量规格（分区+降采样后，趋势查询 30 天 ≤ 3s，常态写入 ≥ 200 样本/s）。

## 二、任务卡

### S8-1 规则引擎：持续时间条件 + 恢复迟滞（P0，对应 G1/G7）

**模型**（V19 迁移）：

- `alarm_template_item` 增列：`duration_sec INT DEFAULT 0`（0=立即触发，行业口径 300~600s 常用）、`hysteresis DECIMAL(18,4) DEFAULT 0`（恢复裕度）；
- 新表 `alarm_condition_state`（rule_item_id, device_id, first_breach_at, last_value, update_time，唯一键 rule_item_id+device_id）：持续条件的"首次越限时刻"持久化（重启不丢）。

**评估链**（AlarmEvaluateServiceImpl）：

- 命中阈值且 duration_sec>0：无 pending 记录则建（first_breach_at=now），不告警；已存在且 now-first_breach_at ≥ duration_sec → 触发告警并清 pending；
- 命中阈值但值回落到 `threshold ± hysteresis` 安全区内 → 清 pending（迟滞防振荡）；
- duration_sec=0 行为与现状完全一致（存量模版零影响）；
- 未命中但有活动告警 → 现有 autoRecover 逻辑不变。

**配套**：

- 阈值导出接口（`/api/ingest/export/thresholds`）透出 duration/hysteresis（网关侧仅透传展示，判定仍在平台）；
- 前端规则行编辑器加两个字段（持续时间/恢复迟滞），V17 基础模版补默认 duration（温度类 300s，漏水/离线保持 0）；
- 分组阈值剖面（G7）仅做设计预留：模版已支持设备级改绑，暂不建"机房剖面"新模型，记录到 P2。

**测试**：duration 未到不告警/到点告警/迟滞防振荡/重启续算 pending/存量模版零影响，≥6 例；`./mvnw test` 全绿。

**验收**：对仿真器做"温度缓升"演练，300s 持续条件在 ~5 分钟整触发；毛刺注入不再产生告警。

### S8-2 告警通知渠道：通用 webhook + 升级策略（P0，对应 G2）

**设计**：

- 新表 `alarm_webhook_channel`（id, name, channel_type: DINGTALK/QYWX/FEISHU/NTFY/TELEGRAM/GENERIC, url, secret, enabled, min_level）；
- 告警分发链（AlarmDispatchService）在邮件/站内之外并行挂 webhook 分发器：按 channel_type 渲染报文（钉钉 markdown、企微 text、ntfy POST body、Telegram sendMessage、GENERIC 原样 JSON）；
- 送达结果记 `alarm_notification_log`（复用现有日志表，channel 字段区分）；失败重试 3 次退避；
- **升级策略**：`alarm_event` 未确认超 N 分钟（默认 15）→ 按渠道组重发并标"升级"（复用审计与通知日志），扫描任务仿 IngestGatewayOfflineMonitorTask。

**测试**：各渠道报文渲染快照测试、失败重试、升级触发，≥8 例；用本地 stub HTTP server 收包验证。

**验收**：钉钉/ntfy 真实收到阶段八验收演练告警；拔掉 webhook 目标 → 日志可见重试与告警不阻塞主链路。

### S8-3 平台存活与静默检测 watchdog（P0，对应 G3）

**设计**（不做带外架构，做"能做的最大子集"+ 部署指引）：

- 新任务 `PlatformSilenceWatchTask`（1 分钟周期）：
  - 静默检测：全平台 metric_sample 最近 N 分钟（默认 5）零写入且存在启用凭证 → 判"采样静默"；
  - 依赖自检：MySQL/Redis/MQTT listener 健康位；
- 触发动作：向 S8-2 的 webhook 通道发 watchdog 事件（部署指引要求 webhook 目标必须位于机房外：公网 SaaS 或办公网）；
- 平台重启时发"上线通知"（可选开关）；
- README 增"带外告警部署指引"：watchdog + webhook 出公网 + 建议机房内保留独立声光报警。

**测试**：静默判定边界（时钟回拨/空凭证集）、watchdog 事件渲染，≥4 例。

**验收**：停掉仿真器全部网关 → 5 分钟内钉钉/ntfy 收到"采样静默"通知；恢复后收到复位通知。

### S8-4 metric_sample 分区表 + 小时聚合（P1，对应 G4/G10）

**设计**（V20）：

- `metric_sample` 改按 `sample_time` 月分区（MySQL 9.6 原生分区；TTL 清理改"drop 分区 + 行级删除混合"）；
- 新表 `metric_sample_hourly`（device_id, point_id, stat_hour, avg/min/max/count，唯一键+索引）；
- 聚合任务：已完成小时增量聚合（仿 TTL 任务节奏）；trend 端点按查询跨度自动路由（≤48h 走原始表，>48h 走 hourly）；
- 观测直方图改滑动 5 分钟窗口（G10 附带）。

**测试**：聚合正确性/边界小时/趋势路由切换/分区裁剪 EXPLAIN 断言，≥6 例。

**验收**：30 天趋势查询 < 3s；容量规格写入 README。

### S8-5 MQTT/存量生态接入适配（P1，对应 G5）

**设计决策（先调研后动手）**：

- 方案 A（推荐起步）：**NUT/ESPHome 桥**——独立小桥接器（或文档化 Node-RED 流）：把 `homeassistant/+/+/state`、NUT UPS 变量映射为平台 ingest 契约（含签名），平台零改动；
- 方案 B（平台内置）：新增"本地集成凭证"类型（broker 侧鉴权替代 HMAC 签名）+ topic 映射规则表——安全边界变化大，需单独 ADR；
- 本阶段先做 A（桥接器 + 文档 + 一个 NUT 演示），B 记录为后续 ADR 候选。

**验收**：一台 NUT（或 ESPHome 模拟发布器）的数据经桥接入库，deviceCode/pointCode 映射符合命名规范。

### S8-6 真实设备寄存器库（P1，对应 G6）

**设计**：

- 新表 `device_modbus_profile`（brand/model/category, register map JSON, scale, 采集建议周期），初始录入 ≥2 款主流型号（温湿度变送器类：建大仁科 RS-*/485 型；UPS：科士达 YDC 系列——寄存器以社区公开文档为准，标注来源与校验状态）；
- 仿真器同步增加这两款"真实设备仿真预设"（寄存器地址/缩放/坏点行为一致）——寄存器库自带测试床；
- 接入流程：管理页选型号 → 填 IP/端口 → 自动建指标绑定（复用类型模版机制）。

**验收**：Node-RED 用该 profile 直接轮询仿真器仿真设备 → 平台出数（把验证 B 的流程产品化）。

### S8-7 CI 流水线（P1，对应 G9）

- GitHub Actions：push/PR 跑 `./mvnw test` + `frontend npm run build` + 仿真器 `mvn test`；缓存 Maven/npm；
- 覆盖率：JaCoCo 报告（暂不设门禁，先出数）；
- 制品：可选 docker image 构建。

### S8-8 前端测试从 0 到 1（P1，对应 G9）

- vitest + @vue/test-utils：优先覆盖本次修过 bug 的面（告警模版编辑保存流、机房工作台 tab 路由、通知队列组件），≥10 例；npm test 进 CI。

### S8-9 下行动作 webhook（P2，对应 G8）

- 告警触发/升级时可选回调外部 URL（规则级开关，超时 3s，失败仅记录）——为"联动风扇/关闸"类场景留钩子，安全注记：仅通知形态，不做控制闭环。

### S8-10 TB 兼容设备 API（P2 候选，需 ADR）

- 提供 `POST /api/v1/{token}/telemetry` 形态的兼容端点（token=凭证映射），直接接住"能说 ThingsBoard HTTP 设备协议"的存量设备——是否做、怎么做（鉴权/限流/类型推断）先出 ADR-008。

## 三、实施顺序与依赖

```
S8-2 webhook ──► S8-3 watchdog（依赖通知渠道）
S8-1 规则引擎（独立，最先做）
S8-7 CI / S8-8 前端测试（独立，穿插进行，尽早建护栏）
S8-4 分区聚合（独立，压测回归前完成）
S8-5 MQTT 桥 / S8-6 寄存器库（依赖 00 清单选型）
S8-9 / S8-10（P2，视前面进度）
```

建议批次：第一批 S8-1 + S8-2 + S8-3（P0 三连，直接命中"告警一定送到、不骚扰人"）；
第二批 S8-7 + S8-8 + S8-4（工程护栏 + 规模）；第三批 S8-5 + S8-6（接入生态）。

## 四、阶段验收（对照 01 目标）

1. 误报告警占比 <10%（30 天窗口，验收演练除外）；
2. 双通道送达 + 升级策略生效（演练留痕）；
3. 静默检测 → 外部渠道通知 → 复位通知全链路演示；
4. 寄存器库两款真实型号接入演示 + NUT 桥演示；
5. CI 全绿 + 前端 ≥10 例；容量规格上 README。
