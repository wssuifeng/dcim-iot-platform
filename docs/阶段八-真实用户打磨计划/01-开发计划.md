## 〇、前置事实（评审确认的设计前提）

1. **设备异常 ≠ 停止上报**：真实网关在设备"值异常"时依然按常规心跳/上报频率推数；只有连接断开才停报，断连由 OFFLINE 规则与网关离线链路兜底。因此基于采样流的告警机制均成立，稀疏采样（长心跳）是唯一需要设计照顾的变量。
2. **正常心跳/上报周期量级**：仿真器默认轮询 5s / 上报 60s；真实网关常见 30s~5min。一切"次数/时间"类机制必须对两种量级都成立。

## 一、任务卡

### S8-1 告警规则增强：三机制 + 一补充（P0，对应 G1/G7）

规则行（alarm_template_item）新增五个可选字段（四项机制），**默认值全部等于"不启用"**（存量模版行为零变化）。默认值调整一律不写 V17（历史迁移已执行、Flyway 不允许修改）；确需给存量温湿度规则开 M1 时，在 V19 内用 UPDATE 显式做，默认仍全关、由用户在界面开启：

| 机制 | 字段 | 启用边界（默认=不启用） | 语义 | 触发行为 |
|------|------|------------------------|------|---------|
| M1 连续越限 | `breach_count INT DEFAULT 0` | ≤1 不启用（首点越限即告警=现状）；≥2 生效 | 连续 N 个采样点越限（"心跳次数内未恢复"）——计数与心跳频率解耦的次数口径 | 第 N 个越限点到达即告警；中途回落进迟滞安全区则清零 |
| M2 变化量 | `rate_limit DECIMAL(18,4) DEFAULT NULL` + `rate_window_sec INT DEFAULT 60` | rate_limit 为 NULL 不启用；非空且窗口内 ≥2 条采样才评估 | 窗口内变化量超过限值（量纲定死：rate_limit = rate_window_sec 窗口内的**变化量**，如 60s 窗口 5℃ 即"每分钟最多变 5"，不是 per-second 斜率） | **直接告警**（不等阈值、不等持续） |
| M3 再告警 | `re_alarm_sec INT DEFAULT 0` | 0 不启用；>0 生效 | 活动告警未恢复且持续越限，距该事件最近一次成功通知已超过 re_alarm_sec | 重发通知（同一告警事件，不改级别，日志记 re-send 口径），避免"一直响"与"持续异常沉默"两头的疲劳 |
| 补充 | `hysteresis DECIMAL(18,4) DEFAULT 0` | 0 不启用；>0 生效 | 恢复裕度 | 恢复判定要求回落进迟滞安全区（方向随算符，见三区模型），防阈值附近振荡 |

**实现总纲：尾部推导，不建状态表**（代码复查定案）：

- 评估链是 `@Async` + AFTER_COMMIT（`AlarmEvaluateServiceImpl.evaluate`），异步乱序/并发下任何 read-modify-write 计数都会丢数，"连续 N 点"的语义在乱序下不成立。因此 M1/M2 的判定基准一律**评估时从 metric_sample 尾部推导**（`ORDER BY sample_time DESC LIMIT N`，现有索引 `idx_metric_sample_device_point_time` 直接支持），**不引入 alarm_condition_state 持久状态表**：
  - 幂等收敛：乱序/重复评估重算同一尾部，结果自然收敛；
  - 重启续算免实现即成立（无内存态、无持久态）；
  - 免去状态行生命周期管理（模板复制/设备改绑/规则行删除都会更换 rule_item_id，状态表会产生孤儿行，需一套清理逻辑）；
  - 代价：每次评估多一条索引范围查询（评估本来就有 findEffectiveRules 查询，量级可接受）。**S8-4 月分区落地后，该尾部查询必须带 sample_time 下界以走分区裁剪**——记为实现注意点。
- **M1 尾部推导细则**：取含当前采样在内的最近 N 条采样，从尾部起数连续越限点数，≥ N 即命中。M1/M2 命中与普通阈值命中**同台竞争、取最严重（级别数字最小）**；M2 命中使用该规则行自身的 alarm_level，与阈值命中共用 METRIC 去重键（同 device+point+METRIC 一个事件），告警文案标注变化量与窗口；
- **M2 基准禁止取 metric_latest**：metric_latest 在 T1 采样事务内、异步评估执行**之前**就已 UPSERT 为当前值，评估读到的永远是"自己"，Δ 恒 0。M2 基准定死为：**以当前采样为终点、向前 rate_window_sec 窗口内最早的一条采样**，命中条件 `|当前值 − 基准值| > rate_limit`；窗口内不足两条（含稀疏采样整窗只有当前一条）或 Δt ≤ 0 → 跳过该机制、回退直接阈值判定。该口径对"窗口内冲高又回落"的往返毛刺不敏感（一阶机制的取舍，接受）；
- **M2 排除累计量指标**：power_kwh 等单调递增累计量禁用 M2（必然命中，PDU 预设 RAMP +0.0222/s 电量即现成反例），在字段说明与前端编辑器注明。
- **防抖在恢复侧，不在触发侧**（状态机约束）：现状态流转表 RECOVERED 只能 → CLOSED，且活动告警去重查询排除 RECOVERED/CLOSED——事件恢复后再次越限**必然新建事件**，"FLAP_MERGED 不新建事件"没有合法流转路径（恢复通知也已发出，合并回去会牵连通知链）。改为 **autoRecover 增加静默窗口条件**：值进入迟滞安全区**且**最近 quiet_window_sec（全局配置，默认 300s）内无越限采样（同样尾部推导）才真正恢复。告警事件数即真实物理事件数，直接支撑"10 分钟内自恢复占比 <10%"的验收口径。
  - 边界兜底：设备恢复正常后**停止上报**（或上报周期 > 静默窗口）的情形下事件会悬挂不恢复——加一个轻量定时任务做"超窗确认恢复"：**最后一条采样已位于安全区、且距今超过 quiet_window_sec、且期间无新越限采样** → 恢复。注意不能简化成"窗口内无采样即恢复"，否则停报时仍越限的告警会被误恢复——数据中断由 OFFLINE/网关离线链路表达，不由恢复链路兜；
  - quiet_window_sec 为全局配置，存 application.yaml（`alarm.quiet-window-sec`，默认 300），本阶段不做库表化。
- **M3 挂点**：`AlarmEventServiceImpl.trigger()` 现有 KIND_SKIPPED 分支（去重跳过，仅 debug 日志）由评估侧接管——活动告警存在且持续越限时，从 alarm_notification_log 推导距最近一次成功通知的时长，超过 re_alarm_sec → 重发通知（不升级、不改级别）。**"成功通知"口径定死**：该事件任一通道 status=1（已投递）的最新一条日志时间，重发成功后同样刷新该基准；M3 仅作用于 METRIC 评估链（OFFLINE/网关离线的重复提醒不在本卡范围）。
- **评估判定改为三区模型（替代现有"未命中→autoRecover"两分支）**：照现有结构直接写会出错——M1 生效后"越限但计数未满"落入未命中分支，会在值仍越限时把活动告警恢复掉。实现按当前值所处区间三分：
  - **越限区**（matches 为真）→ 触发逻辑（直接阈值 / M1 计数 / M2 变化量）；
  - **迟滞死区**（不越限、但未回落进安全区；仅 hysteresis>0 时存在）→ **不动作**：不触发、也不恢复告警。尾部推导口径下死区点同时打断 M1 连续链（死区点不算越限点；恢复侧防抖由安全区判定承担）。安全区方向随算符：GT → `value < threshold − hysteresis`，LT → `value > threshold + hysteresis`（EQ/NE 不适用迟滞，hysteresis 对其无效）；
  - **安全区** → 恢复逻辑（含下述静默窗口判定）。
  hysteresis=0 时死区为空、安全区=不越限，行为与现状一致。

**长趋势判断（评审问题的设计回应）**：采纳兜底原则"趋势不成立→直接执行"。本阶段 M2 变化量即趋势异常的一阶近似（窗口首尾变化量；稀疏采样窗口不足两条时按兜底原则回退直接阈值），完整的基线学习型长趋势（滑动窗口斜率/均值漂移 + 置信守卫）列为 P2 扩展（S8-1b），实现时同样内建"样本不足→回退直接阈值"语义。

**配套改动**：阈值导出接口透出新字段（网关侧仅透传展示，判定仍在平台）；前端规则行编辑器加四字段（M2 字段标注"累计量指标禁用"）。

**测试**（≥10 例）：M1 计数命中 / 中途回落进迟滞区清零；M2 变化量命中 / 样本不足回退直接阈值 / 累计量排除；M3 超时重发通知（成功口径刷新）；恢复侧静默窗口（窗口内再越限不恢复）；三区判定（死区不动作、越限但计数未满不误恢复、迟滞方向随算符 GT/LT）；乱序/重复评估收敛（尾部推导幂等）；默认全关存量零影响。

### S8-2 告警通知渠道：IM webhook 兼容 + 前端配置界面（P0，对应 G2）

**通道现状**：站内铃铛、WebSocket 弹窗、邮件三通道保留不动（注：弹窗本质也是站内形态；实体通道如短信/电话依赖第三方平台能力，属后续专项）。

**新增**：

- 新表 `alarm_webhook_channel`（id, name, channel_type: WECOM/DINGTALK/FEISHU/NTFY/TELEGRAM/GENERIC, webhook_url, credential_json（各平台所需 key/secret/加签配置，结构按渠道文档定义）, **max_alarm_level**, enabled）；
  - 过滤字段命名定案 `max_alarm_level`，语义公式写死：**推送条件 = alarm_level ≤ max_alarm_level**（本项目 1=最紧急、数字越小越紧急；不叫 min_level，避免在"数字小=紧急"体系下实现反向）；
  - credential_json 含敏感凭证，本期明文落库 + 管理权限控制，**加密存储记入长期备忘**（与 S8-4 时序库备忘同册）；
- **凭证与配置全部数据驱动、不写死**：报文模板与加签算法按 channel_type 实现，但 URL、密钥、关键词/secret 等一律来自配置；前端新增"告警通道配置"管理界面（CRUD + 启停 + **测试发送**按钮）；
- **实现纪律：以各平台官方最新文档为准**（钉钉自定义机器人、企业微信群机器人、飞书自定义机器人 webhook 的加签/关键词/频率限制等），实现前逐家核对官方文档并在此任务卡记录文档链接与版本日期，禁止凭印象编造报文格式；
- 分发挂点：`AlarmDispatchServiceImpl` 现有逐通道 try-catch 结构直接扩展，在站内/邮件之外并行挂 webhook 分发器；**失败退避重试 3 次在 @Async 分发线程内同步执行**（间隔如 1s/5s/30s，实现时按各平台官方频率限制校准；不引入新调度器），结果入 `alarm_notification_log`（channel 字段区分）；
- **webhook 事件范围**：ALARM_CREATED / ALARM_UPGRADED / **ALARM_RECOVERED 三类全推**——IM 渠道里恢复也是关键信息，邮件的 D24"恢复不打扰"策略不适用于 webhook；
- **测试发送语义**：前端"测试发送"按钮发一条标注"[测试]"的固定样例报文——不产生告警事件、不入告警分发链，日志 channel 加测试标记，用于用户保存配置后即时验证连通性；
- 与 S8-1 的 M3 再告警共用"同一事件重复通知"的日志口径（re-send 标记）。

**用户侧前置**：用户后续到各平台创建机器人并获取 key（届时填入配置界面即可，代码先行联调用本地 stub）。

### S8-4 采样数据分区与降采样（P1，对应 G4/G10，**已批准**）

维持原方案：V20 按 `sample_time` 月分区 + `metric_sample_hourly` 聚合表，趋势端点按跨度自动路由（≤48h 原始 / >48h 聚合），观测直方图改滑动 5 分钟窗口。

**分区供给任务（方案级缺口，代码复查补齐）**：MySQL **不会自动创建分区**——必须有定时任务提前 CREATE 下月分区（建议每日检查、预建未来 2 个月），供给失败产出告警/日志；缺此任务则跨月首日写入直接失败。

**已知缺陷与长期优化备忘（记入本卡，交付时同步进 README）**：

- 分区键必须在唯一键内（MySQL 限制）：主键需调整为 (id, sample_time) 组合，影响点需回归；
- `ALTER TABLE ... PARTITION BY` 对存量表是**全表重建（COPY）**：实施时写明重建窗口与锁表预期（百万级样本表为分钟级），安排低峰执行；
- 分区粒度=月：TTL 精度下降，保留"drop 分区 + 行级删除"混合清理；
- 当前小时不入聚合表，聚合表存在 ≤1h 滞后；
- S8-1 的尾部推导查询必须带 sample_time 下界，确保分区裁剪生效（两卡联测项）；
- **长期演进**：样本量进入千万级/日或趋势查询仍不达标时，评估迁移时序数据库（TDengine / Apache IoTDB / TimescaleDB / VictoriaMetrics 四选型对比），迁移前提是 ingest 写路径抽象已隔离存储层——本阶段顺带校验该抽象。

**测试**：聚合正确性/边界小时/趋势路由/分区裁剪 EXPLAIN/分区供给任务（缺失时告警），≥6 例。

### S8-5 MQTT 子凭证：存量生态直连接入（P1，对应 G5，**按评审设计执行**）

**问题**：MQTT Ingest 契约要求报文内嵌 HMAC 签名，ESPHome/NUT/HA 等开源生态组件均不支持，存量硬件无法接入。

**方案（评审定稿）**：

- 现有机房凭证体系（AccessKey/SecretKey）基础上，增加 **MQTT 专用子凭证**：每个机房可生成一组独立的 **MQTT 用户名/密码**，与机房 ID 绑定，支持重置；
- 该凭证**仅用于 MQTT 连接层鉴权，不参与 HMAC 签名逻辑**；
- 设备端使用该用户名/密码连接后，平台自动识别归属机房，该连接上报的所有数据归属该机房；
- **标准 HMAC 接口保持不变**，作为标准网关的认证路径，两者共存互不影响；
- 开放通道与签名通道使用不同 topic 命名空间（签名：`dcim/{accessKey}/…`；开放：`dcim-open/{mqttUsername}/…`），机房归属由"username↔topic 前缀一致性 + 凭证映射"双重校验。

**实现要点**：

- **鉴权后端抽象**：连接层鉴权只能落在 broker 侧（平台 MQTT listener 拿不到 CONNECT 报文里的凭证，外置 broker 已由 application.yaml 确认）——实现为 `BrokerAuthProvider` 接口 + mosquitto dynamic-security 默认实现（平台管理账号动态增删 MQTT 用户），预留 EMQX 等适配位，不把 mosquitto 细节泄漏进平台核心；
- **开放通道幂等定义（代码复查补齐）**：存量组件报文不带 seq，去重键降级为 deviceCode+pointCode+**sampleTime**（报文带 seq 时仍优先 seq）；两条键路径共用 ingest 幂等事务边界；
- **报文格式边界（代码复查补齐）**：开放通道只解决**连接层鉴权**，报文体仍须平台 batch JSON schema——ESPHome 原生 sensor schema 的协议适配不在本卡范围；
- 平台 MQTT listener 增开放命名空间订阅，报文直入传输无关核心（机房归属来自凭证映射）；速率限制与最小权限按开放通道口径设计。

**网安**：开放通道纳入后期**专项网安工作**（渗透测试、漏洞挖掘与响应、加固建设），本阶段按最小权限实现并在代码注释标注安全审查点。

**测试**：子凭证 CRUD/重置、错误密码拒绝、username-topic 一致性校验、开放通道入库 + 归属机房正确、无 seq 报文幂等（sampleTime 键）、HMAC 通道回归不受影响，≥6 例。

**验收**：以 ESPHome 客户端身份（其 MQTT 发布能力）用子凭证直连 broker 发布**平台格式**报文，数据入库归属正确机房。

### S8-6 设备接入形态前置事实调研（P1，对应 G6，**✅ 完成 2026-08-31**——结论并入 [ADR-008](../../adr/ADR-008-设备接入形态与TB兼容API边界.md)：形态 A 裸设备经采集网关 / B 智能网关 / C 独立联网自报；预设/寄存器库仅适用 A/B，另行排期）

评审指出：在定义"常见设备预设"之前，必须先区分**设备如何接入云平台**的前置事实。本任务卡改为调研产出：

1. 接入形态分类与取证：
   - 形态 A：普通裸设备（RS485/Modbus RTU）→ **经采集网关**协议转换后北向上报；
   - 形态 B：智能网关（自带多协议驱动，Modbus/SNMP/BACnet…）→ 同 A 但网关智能化；
   - 形态 C：具备独立联网能力的设备（IP 接入，自带 HTTP/MQTT 客户端）→ **自己上报自己的数据**，无需网关；
2. 三种形态各自的：凭证形态（机房 AK/SK vs 子凭证）、上报路径（ingest 两条通道均可）、平台侧建模差异（设备档案由谁建、类型推断是否适用）、典型真实器件举例；
3. 产出：前置事实文档（ADR-008 候选），明确寄存器库（原 S8-6 预设）适用于形态 A/B、形态 C 走 S8-5 类直连——**预设功能与寄存器库随 ADR 结论另行排期**。
