## 一、P0 紧急（1 项）

### W-001 [P0] MQTT 通道在 broker 重连后静默假死（不重新订阅）

- **文件**：`src/main/java/com/example/platform/ingest/mqtt/IngestMqttListener.java:315-330`
- **问题**：`connectAndSubscribe()` 中 `options.setAutomaticReconnect(true)` + `setCleanSession(true)`，订阅仅在首次 `connect()` 后执行一次；全类无 `MqttCallbackExtended.connectComplete` 回调。Paho 1.2.5 在 `cleanSession=true` 时 broker 侧订阅状态随会话丢弃，**自动重连成功后客户端不会自动重订阅**——broker 重启/网络闪断后，MQTT 客户端显示"已连接"但收不到任何消息，直到应用重启。自建的 `scheduleReconnect()`（332-354 行）只在**首次连接失败**时才重订阅，覆盖不到此场景。
- **影响**：真实机房 broker 升级重启是常态，四个 MQTT 订阅（samples/heartbeat/lwt/open）全部静默失效，只剩 HTTP 通道，且无任何自监控能发现。
- **修复**：实现 `connectComplete(boolean reconnect, String serverURI)` 回调，在其中执行 `subscribe(...)`；或将 `automaticReconnect` 关掉统一走自建重连（重连后重订阅）；同时加"最近 N 分钟 MQTT 批次数为 0 且 isConnected=true"的自监控告警。

## 二、P1 重要（15 项）

### 架构韧性

**W-002 [P1] 全部定时任务共享单线程调度器，长任务拖垮离线检测**
- 文件：`src/main/resources/application.yaml`（无 `spring.task.scheduling.pool.size`），任务在 `src/main/java/com/example/platform/task/`
- 问题：7 个 `@Scheduled` 任务共享默认 1 线程池。凌晨 2:00/2:30 的 `MetricSampleCleanupTask`（逐指标批删大表）和 `MetricSamplePartitionTask`（ALTER TABLE DDL）运行期间会阻塞其余全部任务；分区 DDL 遇大表锁等待时，5 分钟级离线检测可能延迟数十分钟。多实例部署时任务还会重复执行（无 ShedLock）。
- 修复：`spring.task.scheduling.pool.size: 4+`；多实例引入 ShedLock；分区 DDL 加超时重试。

**W-003 [P1] @Async 队列打满时 AFTER_COMMIT 抛异常：采样已入库却被记为"写入异常"，告警评估永久丢失**
- 文件：`src/main/java/com/example/platform/config/AsyncConfig.java:20-30` + `IngestCoreServiceImpl.java:95-99`
- 问题：executor 为 core 4 / max 16 / queue 256，未设 `RejectedExecutionHandler`（默认 AbortPolicy）。`AlarmEvaluateServiceImpl.evaluate` 是 `@Async + @TransactionalEventListener(AFTER_COMMIT)`，事件多播发生在 T1 提交线程中；队列满抛 `TaskRejectedException` 会从 afterCommit 回调穿透回 `IngestCoreServiceImpl` 的 catch(Exception)，把**已提交成功**的采样记成 `failed("写入异常")` 返回给网关；同时该采样的告警评估永久丢失。告警风暴时极易触发。
- 修复：设 `CallerRunsPolicy` 或专用无界队列；将"事件发布"与"业务返回"隔离；为评估/分发拆分独立线程池与容量指标。

**W-004 [P1] ingest_dedup 写放大与清理缺陷：无 create_time 索引 + 单条无界 DELETE**
- 文件：`src/main/java/com/example/platform/task/IngestDedupCleanupTask.java:39`，DDL `V11__ingest_channel.sql:30-35`
- 问题：每条采样先 INSERT 一条 dedup 键。`ingest_dedup` 只有 `uk_ingest_dedup(dedup_key)`，无 `create_time` 索引；7 天窗口在 1000 点 × 60s 采样下约 1 亿行。清理任务 `DELETE FROM ingest_dedup WHERE create_time < ?` 单条语句无 LIMIT：全表扫描 + 巨型 undo/binlog，凌晨锁压力可拖垮写入链路。
- 修复：加 `KEY idx_dedup_create_time(create_time)`；清理改 `DELETE ... LIMIT 5000` 循环；高频通道可换 Redis SETEX 一级去重 + DB 兜底。

**W-005 [P1] 批量上报逐条事务 + 每采样 6~8 条语句 + 每条 log.info，高频下吞吐是数量级瓶颈**
- 文件：`IngestCoreServiceImpl.java:84-85` + `MetricSampleServiceImpl.java:266-298`
- 问题：200 条批 = 200 个独立事务，每条采样执行：dedup INSERT、metric_sample INSERT、metric_latest SELECT+UPDATE（读改写非原子）、devices UPDATE（每条刷在线状态）、每条一条 `log.info`，再加 AFTER_COMMIT 异步评估。单批 ≥1200 条语句。`authenticate`（每请求一次 DB 查询，无缓存）与 `refreshLastSeen`（每遥测请求都刷）进一步加倍。
- 修复：`metric_latest` 改 `INSERT ... ON DUPLICATE KEY UPDATE` 原子语义；设备在线状态改 Redis 批量回写；采样级日志降 DEBUG；凭证查询加 Caffeine 短 TTL 缓存。

**W-006 [P2] 批内全部失败无补偿/死信**
- 文件：`IngestCoreServiceImpl.java:91-99`、`IngestHttpController.java:50-60`
- 问题：200 条全失败时仅返回 failures 数组；无失败报文持久化。只有 V25 映射未命中报文才有留存（且每凭证仅 1 条）。网关侧若不处理 failures，数据永久丢失。
- 修复：增加失败采样死信表（保留 24~72h）供补录排障。

**W-007 [P2] Paho 单线程回调串行处理全部消息，慢消费无背压**
- 文件：`IngestMqttListener.java:161-198, 207-256`
- 问题：`handleSamples/handleOpenSamples` 直接在 Paho 回调线程内同步执行（含 200 次逐条事务）。DB 变慢时 QoS1 in-flight 堆积 → broker 重投 → dedup 判重但仍有双倍写放大；极端时 keepalive（30s）超时被踢线。
- 修复：回调内仅入内存有界队列，独立 worker 线程池消费；队满按 QoS 语义丢弃并计数告警。

**W-008 [P2] metric_latest 读改写竞态可回退最新值**
- 文件：`MetricLatestServiceImpl.java:46-75`
- 问题：`getOne` 判存 + UPDATE 非原子：并发写同一 (device,point) 时，较旧采样可在较新事务提交后覆盖 `latest_time`，最新值回退。
- 修复：改 `INSERT ... ON DUPLICATE KEY UPDATE latest_value=IF(sample_time>latest_time,...)` 单语句原子化。

### 协议兼容性

**W-009 [P1] 二进制协议完全无法接入（V25 映射仅支持 JSON）**
- 文件：`PayloadTranslationEngine.java` 全文、`IngestPayloadMappingServiceImpl.tryTranslate`
- 问题：路径语法只支持 JSON 点路径/数组下标；非 JSON 报文 `readTree` 失败 → 映射必然不命中 → 留存原始报文 + 422。真实 DCIM 里 Modbus RTU/TCP 透传帧、电力 645 协议的网关若以 hex/base64 二进制上报，本平台只有"接转换网关"一条路。
- 修复：最低成本方案：开放通道增加 `encoding=hex|base64` + 寄存器偏移映射模板（起始寄存器/数据类型/字节序/scale），即可覆盖 Modbus 类设备；或文档明确"必须前置协议网关"。

**W-010 [P1] TB 兼容通道绕过 200 条批上限，且流量不可观测**
- 文件：`TelemetryCompatController.java:104-131`
- 问题：`parseBatch` 手工 new `IngestSampleBatchDTO` 塞 items，不经 `validator.validate(batch)`，`@Size(max=200)` 被完全绕过——单请求传 10 万条数组会变成 10 万个逐条事务，DoS 面。且该 Controller 全程未调 `metricsCollector.recordBatch`，监控看不到 TB 通道流量。
- 修复：解析后执行 `validator.validate(batch)` 并超限截断/拒绝；补 `recordBatch("tb", ...)` 埋点。

**W-011 [P1] MQTT HMAC 签名对象是 Jackson 重序列化结果，与网关序列化强耦合**
- 文件：`IngestMqttListener.java:174-175`
- 问题：验签时 `objectMapper.writeValueAsBytes(batchNode)` 把解析后的子树重新序列化再 `sha256(secret+bytes)`。任何与 Jackson 输出的字节差异（键序、数值格式 `1.0` vs `1`、unicode 转义）都会导致验签失败整包丢弃——真实网关不恰好是 Jackson 的紧凑格式。
- 修复：envelope 增加 `batch` 为**字符串字段**（网关对自身原始串签名，平台取字符串验签后再 parse）；或对整个 payload 字节签名。

**W-012 [P2] 时钟漂移容忍不对称 + 7 天 dedup 窗口外的"补传"必重复落库**
- 文件：`GatewaySignUtils.java:79-84`、`IngestDedupCleanupTask.java:38-42`、`MetricSampleServiceImpl.java:81`
- 问题：未来 >5min 拒绝，但过去无下限：设备时钟回拨/长期离线补传合法。无 seq 通道的幂等键含 sampleTime，同一采样在 dedup 7 天窗口过期后重发会作为新数据落库。
- 修复：文档化 seq 清零需网关换 deviceCode 或平台加 seq 纪元；sampleTime 增加"早于 N 天拒绝"可配置项。

**W-013 [P2] 设备离线检测最坏延迟 ≈ 20 分钟**
- 文件：`application.yaml:93-95`（5 分钟扫描）+ `V17__base_alarm_templates.sql:24`（OFFLINE threshold=15 分钟）
- 问题：最坏 15+5=20 分钟才知道设备挂了，且模板阈值是分钟整型无秒级。对"空调停机/漏水"类场景偏慢。
- 修复：文档明确延迟；模版阈值支持秒级；关键设备走"最后采样时间"实时判离线。

**W-014 [P2] TB T1 形态强制丢弃名为 `device`/`ts` 的业务键**
- 文件：`TelemetryCompatController.java:155-165`
- 问题：`if ("device".equals(key) || "ts".equals(key)) continue;`——设备真有叫 `ts` 的指标（时间戳指标很常见）会被静默吞掉。
- 修复：T2 形态才跳过 `ts`；T1 仅跳过 `device` 并对 `ts` 冲突给告警日志。

### 数据层性能

**W-015 [P1] 小时聚合无补跑窗口，停机 >2h 造成永久数据空洞**
- 文件：`MetricSampleHourlyAggregationTask.java:32-42`
- 问题：聚合窗口固定 `[now-2h, now)`。应用停机 3 小时或聚合连续失败超过 2 小时，中间小时桶永远缺失；原始数据随后被保留策略删除，>48h 趋势查询永久缺段。
- 修复：启动时及每轮改为"从 `metric_sample_hourly` 最大 bucket_start 补到当前小时"；给聚合任务加水位表。

**W-016 [P1] 生产环境 MyBatis SQL 全量打 stdout**

- 修复：prod profile 覆盖为 `NoLoggingImpl` 或默认 `SLF4JImpl` + mapper debug 级别。

**W-017 [P2] 分区自愈有盲区**
- 文件：`MetricSamplePartitionTask.java:56-66`
- 问题：供给失败告警本身要写 DB——若故障根因正是 DB，告警也写不进去；任务仅每日 00:15 一次，应用重启不检查分区。
- 修复：`ApplicationReadyEvent` 时执行一次 `ensureFuturePartitions`；告警失败时降级打 stdout+邮件直发。

**W-018 [P2] Druid prod 连接池与写入模式不匹配**
- 文件：`application-prod.yaml`（max-active: 50, max-wait: 60000）

- 修复：max-active 上调或 max-wait 降到 5~10s 快速失败。

**W-019 [P2] 30 天趋势尾部缺最近 1-2 小时**
- 文件：`MetricSampleServiceImpl.java:200-207`

**W-020 [P2] ingest_raw_message 每凭证仅 1 条，调试窗口过窄**
- 文件：`V25__payload_mapping.sql`（`uk_raw_message_credential`）
- 问题：新报文覆盖旧报文：调试时设备一秒一条、报文有 A/B 两种形态，配置页永远只看得到最后一条。
- 修复：每凭证环形保留 N 条（如 20）并截断至 64KB。

### 安全与审计

**W-021 [P1] HMAC 签名无时间戳/nonce，抓包重放永久有效**
- 文件：`GatewaySignUtils.java:30-36`、`GatewayAuthenticationFilter.java:86`
- 问题：`signature = sha256(secret + rawBody)` 无时效成分：同 body 重放在 7 天 dedup 窗口内被判 duplicated（无害），**窗口过后重放则原样再落一遍库**（数据污染）。MQTT LWT/heartbeat 甚至无签名。
- 修复：增加 `X-Gw-Timestamp`（±5min 窗口）参与签名；可选 nonce+Redis SETNX 防重放；heartbeat 报文纳入验签。

**W-022 [P1] MQTT broker 默认匿名 + dcim-open 通道可被注入伪造数据**
- 文件：`docker/mosquitto/mosquitto.conf`（`allow_anonymous true`）、`docker-compose.yml:57-64`（1883 映射宿主机）、`IngestMqttListener.java:207-256`
- 问题：默认部署下任何人可匿名 `subscribe dcim-open/#` 嗅探全部 topic（拿到合法 username），随后 `publish dcim-open/{username}/samples` 注入数据。匿名者也可向 `dcim/{accessKey}/lwt` 发遗嘱触发假离线告警。
- 修复：`broker-auth=none` 时禁用/警告开放通道；compose 默认启用 DynSec；生产强制 `allow_anonymous false`。

**W-023 [P1] Redis 故障期间 Token 黑名单整体失效**
- 文件：`TokenBlacklistService.java` + `CacheServiceImpl.get/hasKey`
- 问题：黑名单读写走 CacheService 的"静默降级"语义：Redis 挂掉时 `isTokenBlacklisted` 返回 false、写入丢失仅 warn。**安全黑名单没有 DB 兜底**，降级语义与安全语义冲突——注销/禁用用户在 Redis 故障期间重获访问权。
- 修复：黑名单类 key 读写失败改为抛异常拒绝请求（fail closed），或黑名单落 DB/本地 Caffeine 二级兜底。

**W-024 [P2] JWT 2 小时过期且无 refresh 机制**
- 文件：`application.yaml`（`jwt.expiration: 7200`）、`AuthController.java`
- 问题：值班大屏/移动端每 2 小时被登出（WebSocket 同断）。
- 修复：增加 refresh token（长 TTL + 旋转）或滑动续期。

**W-025 [P2] XSS 面：XssFilter 不覆盖 JSON 体与 WebSocket**
- 文件：`XssRequestWrapper.java`、`InAppNotificationServiceImpl.java:130-150`
- 问题：JSON body（告警消息、规则名、设备名等）不经过滤器清洗；WS 推送直达前端。当前前端无 v-html/innerHTML，风险被输出端转义兜住——但这属于隐式依赖。
- 修复：对 `alarm_message/rule_name/device_name` 入库前做 HTML 清洗；增加 CSP 响应头。

**W-026 [P2] 限流过滤器对机器通道一刀切且信任 XFF**
- 文件：`RateLimitFilter.java:63-75, 110-125`
- 问题：`/ingest/**` 与用户页面共用同一 IP 桶：多设备经 NAT 出口上报可误触 429（TB SDK 收到 429 后退避，真实表现为数据断流）；`extractClientIp` 无条件信任 `X-Forwarded-For`，攻击者可伪造 XFF 绕过限流。
- 修复：机器通道按凭证维度限流（Redis）而非 IP；XFF 仅在可信代理后启用。

**W-027 [P2] ProductionSafetyGuard 覆盖不全**
- 文件：`ProductionSafetyGuard.java:39-53`
- 问题：已覆盖 JWT/CORS/Redis/DB 密码，但未校验：`verification.hmac-secret` 默认值、`ingest.mqtt.broker-auth=none`、broker 匿名。
- 修复：补上述三项校验。

### 告警引擎正确性

**W-028 [P1] trigger() check-then-insert 竞态 + 级别升级无锁，可产生重复活动告警**
- 文件：`AlarmEventServiceImpl.java:109-153`、DDL `V4`（`idx_alarm_event_dedup` 仅普通索引非唯一约束）
- 问题：评估是并发的（@Async 池 16 线程），两个线程同时对同一 (device,point,METRIC) 评估：都 `findActiveEvent` 返回 null → 各自 save → **两条活动告警**。级别升级同样是 read-modify-write（:134-149），并发升级互相覆盖。
- 修复：为活动告警建"软唯一"（可空列 active_key = device:point:type，RECOVERED 时置 null + 唯一索引），insert 捕获 DuplicateKeyException 转升级分支；升级用 `UPDATE ... WHERE alarm_level > ?` 原子 CAS。

**W-029 [P1] GATEWAY_OFFLINE 全局单槽：多网关互相顶掉、恢复错人**
- 文件：`AlarmEventServiceImpl.findActiveEvent:378-397` + `IngestGatewayOfflineMonitorTask.java:44-83`
- 问题：去重键仅 deviceId+pointId+alarmType，GATEWAY_OFFLINE 类型 deviceId 均为 null → 全局单槽。机房 A 网关离线告警活动期间，机房 B 触发被 SKIPPED；任一网关心跳恢复即 `autoRecover(null,null,GATEWAY_OFFLINE)` 恢复"最新一条"——**可能 B 还离线着，A 的恢复把 B 的告警也关了**。真实机房多网关是标配。
- 修复：AlarmTriggerContext 增加 credentialId 维度进入去重键。

**W-030 [P1] "从未上线"告警永不自动恢复**
- 文件：`IngestCredentialServiceImpl.java:254-268`
- 问题：`wasStale = lastSeenAt != null && stale`——`lastSeenAt == null`（从未上线场景）的凭证首次成功上报后 `wasStale=false`，不调用 autoRecover；`IngestGatewayOfflineMonitorTask` 只有触发方向没有恢复方向。该告警**永久悬挂为活动告警**，并持续压制后续 GATEWAY_OFFLINE 触发（同型去重）。
- 修复：`lastSeenAt == null → lastSeenAt 非空` 的状态迁移同样触发 autoRecover。

**W-031 [P1] 每条采样触发一次全量评估，模板规则零缓存**
- 文件：`AlarmEvaluateServiceImpl.java:111-157`
- 问题：每采样 AFTER_COMMIT 异步执行：`findEffectiveRules(deviceId, pointId)`（涉及 device→type→template→items 多表链）+ 每条规则可能的 M1 尾部范围查询 + M2 基线查询，REQUIRES_NEW 事务。100 点设备 10s 采样 = 每秒 10 个评估任务、30+ 条查询。批 200 条上报 = 200 个评估任务瞬间灌入 queue 256 的池。
- 修复：模板规则按 device/point 缓存（变更时失效）；同 (device,point) 1 秒内合并评估；M1/M2 查询走覆盖索引并限制回看条数。

**W-032 [P2] M1 streak 跨时间断裂不重置**
- 文件：`AlarmEvaluateServiceImpl.java:206-230`
- 问题：连续越限计数仅按 sampleTime 顺序回看，不考虑采样间隔：设备离线 1 小时后首包若越限，且离线前尾部也是越限，streak 直接续上立即告警（应视为新事件）。
- 修复：相邻两样本间隔超过 N 倍正常周期即断链。

**W-033 [P2] 恢复侧静默窗口 LIMIT 500 兜底会漏检**
- 文件：`AlarmEvaluateServiceImpl.java:336-344`
- 问题：5 分钟窗口内采样 >500 条（秒级设备）时只检查最新 500 条，窗口前段越限样本漏检 → 提前恢复。
- 修复：改为 `SELECT EXISTS(越限样本 in window)` 让索引判断。

**W-034 [P2] 告警风暴与分发共用 16 线程池，webhook 同步重试放大占用**
- 文件：`AlarmWebhookDispatcherImpl.java:47`（退避 1s/5s/30s）+ `AlarmDispatchServiceImpl.dispatch`（@Async）
- 问题：单告警分发最坏占用 async 线程约 2 分钟（3 次重试等待+5s 超时×3），风暴时与评估任务争抢同一线程池，加剧 W-003 的拒绝问题。
- 修复：分发独立线程池；重试改异步延迟队列而非线程内 sleep。

### 可观测性与运维

**W-035 [P2] TraceId 对 MQTT 与定时任务不覆盖**
- 文件：`AsyncConfig.java:32-47`、`IngestMqttListener.java:161-198`、全部 task/ 类
- 问题：MQTT 回调线程与 `@Scheduled` 线程的 MDC 为空，日志无 traceId；MQTT 拒收审计无法与网关侧排障关联。
- 修复：MQTT 处理入口手动 `MDC.put(traceId)`（可用 messageId/UUID）；调度任务用任务名作 traceId。

**W-036 [P2] 系统自监控仅 PARTITION_SUPPLY_FAILED 一种**
- 文件：`MetricSamplePartitionTask.java`（唯一自指告警）、`application.yaml` actuator 仅暴露 health,info
- 问题：MQTT 断连（含 W-001 假死）、async 队列深度/拒绝次数、Redis 降级、dedup 清理失败、聚合失败都只落日志。
- 修复：接入 Micrometer，暴露 `/actuator/metrics/prometheus`；对关键指标做巡检告警。

**W-037 [P2] Flyway 无回滚策略**
- 文件：`db/migration/`（V1~V25 全部前向），`V21`（注释自述 PARTITION BY 为全表重建）

- 修复：发布前强制 mysqldump/云快照 + 演练；破坏性迁移拆分 expand→migrate→contract 三段；部署手册补故障预案页。
