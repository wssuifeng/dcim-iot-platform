## 二、维度调研

### D1 告警规则引擎

| 平台 | 规则模型 | 评估方式 | 生命周期 | 通知 | 与本项目三机制对照 |
|------|---------|---------|---------|------|------------------|
| **ThingsBoard CE** | "Rule Chains"（规则链，可视化编排器，节点化组成） | 事件驱动 | 报警对象有状态机（未读→已确认→已关闭），可分派与升级 | 通知节点（邮件/SMS/webhook/SMS） | 规则链 vs 我们的告警模版：方向不同——TB 是"事件处理器"，我们是"规则集"；本项目 streak/windowDelta/resend 三机制 TB 无直接对应 |
| **JetLinks** | 统一规则引擎，设备告警 + 场景联动共用；可"自定义规则模型"；模块树有 `rule-engine-component` + `rule-engine-manager` | 实时流（响应式） | 未提及（README） | 未提及 | "告警由规则引擎统一管理"和我们 V15 模版类似，但响应式实现值得看代码 |
| **ThingsPanel** | "Rule Engine"特性："Data forwarding to third parties, receiving device data and converting, accessing various protocols, real-time data calculations"——不是传统阈值告警引擎，而是**数据路由+实时计算+协议转换** | 实时流 | "Alarm Information" 列表（按项目/分组/时间过滤）——有告警对象但未细说生命周期 | 通知特性：SMS/邮件/电话/webhook | 与本项目最不对齐：TP 把规则引擎定位为"数据流向与转换"，本项目规则引擎是"告警模版"——定位不同 |
| **Zabbix** | 触发器表达式（`{host:key.fnc(params)}=value`），可多条件组合、时间窗口、复合触发器；trigger dependency 显式定义抑制 | 周期拉取或 trap 推送 | 触发器事件→事件→告警→多级升级（escalation，可定时多步通知）；支持维护期静默 | 媒介（Media type）注册，脚本扩展，告警分级 + RCA | **告警引擎的成熟度标杆**。trigger expression + escalation + dependency + 维护期 完整闭环——本项目三机制是其子集 |
| **Alertmanager** | YAML 配置 route/group_by/group_wait/group_interval/repeat_interval + inhibit_rules（source/target matchers） | 被动接收（来自 Prometheus server） | 完整五件套：**去重 / 分组 / 路由 / 抑制 / 静默** | receiver 多种（email/PagerDuty/OpsGenie/webhook）；HA 默认开启（gossip） | **告警生命周期语义的工程模板**。我们的"通知日志去重"实现可对照其"去重 + 路由树" |
| **LibreNMS** | 未提及（README） | — | — | — | — |
| **NetBox** | "Automated Events"——用户定义 event rule 触发自定义 script / 出站 webhook | 事件钩子 | 无告警生命周期 | 触发 webhook | 与本项目"下行动作 webhook"类似，但定位是"事件钩子"非"阈值告警" |
| **OpenDCIM** | 未涉及（README） | — | — | — | — |

**结论**：D1 域里"业务链完整"的平台分两派：
- **告警引擎派**（Zabbix、Alertmanager）——把告警作为核心能力，规则/抑制/升级/静默独立建模
- **数据流引擎派**（TB、JetLinks、TP）——告警内嵌在"数据处理管道"里（规则链/响应式流/规则引擎），弹性大但复杂度高

本项目现状（V15 模版 + V19 三机制 + V20 通知渠道 + V22 下行动作）整体偏"告警引擎派"，但实现细节可向两派学习。**阶段二代码深挖重点**：TB 的 rule-chain 节点模型、JetLinks 响应式流式评估。

**结论**：D2 域里"能跑通 DCIM 业务链"的项目分三类：
- **平台自研协议包**（TB / JetLinks）—— 适配器 + 设备 profile
- **侧重南向采集**（TP / Zabbix / LibreNMS）—— 从设备主动采集
- **只收北向不做采集**（Alertmanager / NetBox / OpenDCIM）—— 定位不同

本项目与 TB/JetLinks 同行（北向契约），但**不南向采集**（ADR-002）是已定非目标。**阶段二重点**：JetLinks `network-component` 与 `protocol-component` 的模块边界定义；TB 的 device profile 字段模型。

### D3 报文处理与自定义转换

| 平台 | 预设报文形态 | payload 解析 | 自定义转换 | 物模型 |
|------|------------|-------------|-----------|-------|
| **ThingsBoard CE** | 协议插件内含默认 payload 解析器 | "Transform and normalize your device data" | 规则链中的脚本节点（JS） | "Device Profile"——抽象的设备物模型 |
| **JetLinks** | "不同厂商不同报文统一接入" | `protocol-component` 模块 | "自定义规则模型"——`script-component`（脚本支持） | `things-component`（物组件） |
| **ThingsPanel** | 协议插件自带（Modbus/TCP/GB28181...） | "Device Configuration Templates" 把"协议配置+数据处理+自动化+告警+扩展信息"绑成模板 | 协议插件可自定义 | "Device Function Templates"——物理模型 + 图表 |
| **Zabbix** | "stream metrics and events over HTTP" | 触发器表达式解析 | 媒介脚本 | "Items" + "Templates"——预置指标模板，可复用 |
| **Alertmanager** | 标签（label）匹配 | YAML 路由树 | matchers + 正则（`=~`） | 标签 annotation 模型 |
| **LibreNMS** | MIB/OID（README 未展开） | — | — | — |
| **NetBox** | 不采集 | — | — | 完整数据模型（机柜/设备/端口/IP） |
| **OpenDCIM** | SNMP 协议 | — | — | 设备/机柜/电力回路 |

**结论**：D3 是差异最大也最值得学的领域。三个"自研协议"平台（TB / JetLinks / TP）的共性：
- **协议插件化**（独立模块/包，物理隔离）
- **payload 解析与规则解耦**（解析在协议包，规则在引擎）
- **物模型独立建模**（设备 profile / things-component / function template）

本项目 V25 自定义报文映射（ADR-009）已经实现"特征匹配 + 字段路径转译 + dry-run + 原始报文留存"，与三平台属同一类能力。**差异**：本项目没有"协议插件框架"——本项目只做 4 通道 + 映射回退，不支持第三方写协议包；这与"轻量化"定位一致。

**阶段二重点**：TB rule chain 节点分类；JetLinks script-component 的脚本能力边界（避免像本项目一样禁用 DSL 安全）；TP "Device Configuration Templates" 的字段定义。

| **Zabbix** | 主机/监控项 + Template | 时序 + 触发器 | graphs/lists/geomaps/网络拓扑 | 网络/服务器，无机房 | 🔶 |

| **OpenDCIM** | — | — | — | 机柜/设备/电力回路 | ✅ 资产管理（领域次强） |

**结论**：D4 暴露了一个清晰的事实——**没有一家开源平台同时具备"实时告警引擎 + DCIM 领域模型"**。本项目正好在"通用 IoT 平台"的 D4 留白（🔶 标记的）和"资产型 DCIM"的留白（✅ 标记但实时告警是 ⬜）的中间。这正是你的定位"对标主流非商业方案的轻量化 DCIM"被证明有价值：不是"做同样的事"而是"填补一个生态空位"。

**阶段二重点**：NetBox 数据模型层级（Device → ModuleBay → Interface → Cable）作为本项目"机房/机柜建模"的扩展参考——若你判断 DCIM 领域要加深，可学；本项目当前"机房=接入主体"模型已够用。

## 三、跨维度启示（学什么、做什么、做到什么程度）

### 可直接借鉴的（**D1+D3 域，告警与报文处理**）

1. **告警"去重/分组/路由/抑制/静默"语义模型**（来自 Alertmanager）——本项目"通知日志去重"实现可补齐分组路由维度
2. **trigger expression + 复合触发器**（来自 Zabbix）——本项目模版规则的"复合条件"是否够用？阶段二比对
3. **"协议插件化 + 解析与规则解耦"架构**（来自 TB/JetLinks）——本项目 4 通道+映射回退属"轻量插件化"，但**不支持第三方写协议包**是有意轻量化裁剪（与"轻"一致）
4. **Device Function/Profile Template**（来自 TP）——本项目"告警模版"是同质能力，已在 V15 实现，可对照 TP 字段分类
5. **payload 留存+dry-run 预览**（本项目自创，V25）——三平台均无原始报文留存，**这是本项目差异点**，写论文时可提

### 明确不做的（**D5 域，部署体量**）

- 不做规则链可视化编排（TB/重引擎）——轻量化定位与之冲突，已写进非目标
- 不做南向协议采集（TP/Zabbix/LibreNMS 路线）——ADR-002 已定
- 不做多租户（TB/JetLinks/TP）——ADR-001 已定
- 不做部件市场（TP 的"应用市场"）——非目标已加

### 待定的（**D4 域，DCIM 深度**）

- **是否做机柜/U 位建模**（NetBox 路线）？当前本项目"机房即接入主体"模型未覆盖机柜层级——如果对标 NetBox，需要 C5 升级。**建议先做调研补 D4 章节，第二阶段定**
- **是否做 SCADA 大屏**（TP 路线）？当前驾驶舱+工作台已满足开箱演示，暂不需要

## 五、调研结论与下一步

1. **生态空位确认**：没有开源平台同时具备"实时告警引擎 + DCIM 领域模型"——本项目定位合理，**不是竞争，是填空**
2. **轻量化对标应锁两阵营**：TP（轻量化 IoT 平台）+ Alertmanager 思路（告警生命周期工程模板）。TB 仍作为功能对标对象但其部署体量不是本项目目标
