## 一、核心问题直接回答

**本项目能否接真实设备？** —— **能接 70-80% 的真实设备，但有明确边界**。

| 设备类别 | 能否接入 | 接入路径 |
|---------|---------|---------|
| 标准 MQTT 设备（4 协议内） | ✅ | V11 ingest 门，HMAC 签名 |
| ThingsBoard 生态设备 | ✅ | ADR-008，TB SDK 9/9 实测 |
| 经第三方平台/网关 MQTT 子凭证 | ✅ | V24，MQTT 子凭证通道 |
| 标准 JSON 报文的私有协议设备 | ✅ | ADR-009，特征匹配 + 路径转译 |
| 智能电表/UPS/精密空调等标准 Modbus TCP 设备 | ❌ | **未实现** Modbus 接入 |
| SNMP 设备（路由器、UPS 带 SNMP 网卡） | ❌ | **未实现** SNMP 接入 |
| CoAP 设备（NB-IoT 终端） | ❌ | **未实现** CoAP 接入 |
| PLC / 串口直连设备 | ❌ | ADR-002 明确不南向采集 |
| 消防/动环带 SIP 协议 | ❌ | 未实现 |
| LwM2M 设备 | ❌ | 未实现 |

**关键边界**：本项目 **不实现任何南向协议**（ADR-002），只接收网关北向 JSON 契约。
对真实机房来说，**只要有第三方网关做了协议翻译**（如主流的串口服务器、网管
网桥、动环主机），本项目就能接；**没有第三方网关做翻译的纯串口/Modbus 设备**，
需要外部网关补齐——**本项目自己不解决这个 gap**。

## 四、要接 100% 真实机房设备，缺什么？

按差距从小到大排列（每条都对应差距清单条目）：

| 缺口 | 工作量 | 必要性 | 差距编号 |
|------|--------|--------|----------|
| **C14 轻量化两条判据实测**（≤2GB/4 核 + ≤30 分钟开箱） | 小（实测脚本） | 高（论文素材） | G-010 |
| **C13 设备寄存器库首批 5 真实器件** | 中（每器件查手册） | 中（差异化卖点） | G-009 |
| **Modbus TCP 接入**（T3 阶段九后续卡之一） | 大（4 周） | **高**（工业动环主流协议） | 新增 G-013 |
| **MQTT broker 集成 adaptive mTLS / OneNET 等私有云隧道** | 中 | 中 | 视需求 |
| **设备 LWT（遗嘱）消息处理为设备离线告警事件** | 小（已部分实现于 V11） | 高 | 已实现 |
| **解析器可视化测试台**（类似 V25 dry-run 的 GUI 化） | 中 | 低 | 视需求 |

**最大缺口是 Modbus TCP**——这是动环监控真实现场最主流的协议（智能电表、UPS、精密空调、漏水检测器、电池巡检等几乎都走 Modbus 寄存器）。本项目**不实现 Modbus** 但有 3 个变通路径：
- **变通 A**：让真实机房现场有 Modbus 网关（如有人物联网、亿佰特 RS485-TCP 转 MQTT 网关，约 200-500 元/台），网关把 Modbus 寄存器翻译成 JSON 报上来——本项目 100% 能接
- **变通 B**：本项目加一个"Modbus 边采进程"独立子项目（参考 TP 的 `modbus_service:503`），把 Modbus 寄存器读出来发到我们 ingest 门的 MQTT 通道——**工作量大但可控**
- **变通 C**：用 JetLinks 的协议 jar SPI 机制，引入 Modbus 协议 jar（社区/商业有成熟实现）

## 七、Alertmanager 告警生命周期工程实现（补充调研）

> 仓库 `D:\code\repos\alertmanager`（6.7MB，master 直接克隆）。
> Alertmanager 的核心不是"产生告警"而是"告警产生后的治理"——五件套去重/分组/路由/抑制/静默。
> 以下为源码直接阅读结论。

### 7.1 告警数据模型（alert/alert.go）

```go
type Alert struct {
    model.Alert  // Labels, Annotations, StartsAt, EndsAt, GeneratorURL
    UpdatedAt time.Time  // 权威时间戳（merge 判序用）
    Timeout   bool
}
```

- **活跃 vs 恢复判定**：`EndsAt` 在未来 = firing，已过 = resolved
- **Merge 方法**：按 `UpdatedAt` 判序，保留最早 startsAt、最晚 endsAt，**annotations 按新覆盖旧**——同一告警多次上报时自动去重合并

### 7.2 去重机制（notify/dedup_stage.go）

核心：**NotificationLog（nflog）+ GroupKey + hash 哈希**。

- 每条告警通过 `hashAlert(a)` 生成 uint64 指纹（labels 哈希）
- 同一 GroupKey 的 firing/resolved 集合用 hash 集合比对（`partitionAlertsByState` :99-116）
- `needsUpdate()`（:52-96）六种通知原因：
  1. `ReasonFirstNotification`：首次通知（entry==nil 且有 firing）
  2. `ReasonNewAlertsInGroup`：组内新增告警（firing 子集变化）
  3. `ReasonAllAlertsResolved`：全部恢复（必须通知，清 nflog）
  4. `ReasonNewResolvedAlerts`：新增恢复通知（SendResolved 开启时）
  5. `ReasonRepeatIntervalElapsed`：重复间隔到期（周期提醒）
  6. `ReasonDoNotNotify`：不需要通知
- **对本项目的启示**：我们 `AlarmNotificationLog` 的去重是"告警级"，Alertmanager 的去重是"通知级 + 分组级 + 周期级"三层。补齐方向：给通知加"同组新增告警不重复通知整个组"的增量逻辑

### 7.3 分组机制（dispatch/）

- `AggregationGroup` 按 `group_by` 标签分片，每个组一个 goroutine
- `group_wait`：首次通知前的等待窗口（等更多告警聚合成组）
- `group_interval`：组内新告警加入后到下次通知的间隔
- `repeat_interval`：无变化时的周期重复通知间隔
- **对本项目的启示**：本项目告警弹窗已有"手动关闭队列 + 堆叠上限"，但没有"分组聚合"——同一机房多设备同时告警会弹 N 个弹窗。可借鉴 `group_by = [roomId, alarmLevel]` 思路

### 7.4 路由机制（dispatch/route.go）

```go
type Route struct {
    Matchers labels.Matchers  // 告警必须匹配才走此路由
    Continue bool              // true = 匹配后继续匹配同级路由
    RouteOpts               // group_by/wait/interval/repeat/receiver
    Routes []*Route          // 子路由（树形递归）
}
```

- matcher 语法：`=`, `!=`, `=~`, `!~`（labels.Matchers）
- 树形路由：根 → 子路由递归匹配，`Continue` 控制是否穿透
- **对本项目的启示**：我们的通知渠道是"级别过滤"平铺；可借鉴路由树思想——`alarmType=DEVICE_OFFLINE → 企微渠道`，`alarmLevel<=2 → 电话+企微`

### 7.5 抑制机制（inhibit/inhibit.go）

```go
type InhibitRule struct {
    SourceMatchers []Matcher  // 源告警（触发抑制的）
    TargetMatchers []Matcher  // 目标告警（被抑制的）
    Equal          model.LabelNames  // 源和目标必须相等的标签
}
```

- 语义：当存在活跃的源告警且源与目标在 `Equal` 标签上取值一致时，目标告警被抑制（不发送通知）
- 例：`source={alertname=DatacenterFire, severity=critical}` + `target={severity=~"warning|major"}` + `equal=[datacenter]` → 机房着火时抑制同机房的所有 warning/major
- **无时间窗口**：抑制只在源告警活跃期间有效，源恢复后自动解除
- **对本项目的启示**：我们的"级别升级"（数字小 = 更紧急）已实现"高级别覆盖低级别"，但**没有"高级别活动时抑制同设备低级别"**——可以作为一个 V26 方向

### 7.6 静默机制（silence/silence.go）

- `Silence` 结构体：Matchers + StartsAt + EndsAt + CreatedBy + Comment
- **全局生效**：不挂在路由树上，独立于路由（告警先过静默过滤，再进路由）
- 与抑制的区别：静默是**人工操作的定时屏蔽**（值班人员"凌晨维护窗口别吵我"），抑制是**规则驱动的自动关联抑制**
- **对本项目的启示**：本项目完全没有静默机制——机房维护窗口期间会持续触发告警。这是**运维刚需**，建议列入 G-014

### 7.7 通知重试（notify/retry_stage.go）

- **指数退避**（`backoff.NewExponentialBackOff()`）：每次失败后等待时间翻倍
- **无最大重试次数**：`backoff/v5 的 ExponentialBackOff 从不返回 Stop`——**无限重试直到 context 超时/取消**
- Integration 的 `Notify()` 返回 `(retry bool, err error)`：非可恢复错误直接停止
- **对本项目的启示**：我们的 webhook 重试是 1s/5s/30s 三次固定退避，**无无限重试兜底**；但"无限重试"在告警风暴时可能放大问题——建议改为"指数退避 + 最大 10 次 + 超时 5 分钟"折中

### 7.8 对本项目的差距总结

| 告警生命周期环节 | Alertmanager | 本项目现状 | 建议 |
|-----------------|-------------|-----------|------|
| 告警去重 | hash 指纹 + nflog 通知日志 | AlarmNotificationLog（有） | 已实现，可补组级增量 |
| 告警分组 | group_by + AggregationGroup | ❌ 无分组（弹窗堆叠上限） | G-014 补分组聚合 |
| 告警路由 | 树形 Route + Matchers | 级别过滤平铺 | 低优先级 |
| 告警抑制 | InhibitRule（源→目标+equal） | ❌ 无抑制（有级别升级） | V26 方向 |
| 告警静默 | Silence（人工定时屏蔽） | ❌ 无静默 | **G-014 高优先级** |
| 通知重试 | 指数退避 + 无限直到超时 | 1s/5s/30s 三次固定 | 可改为指数退避+上限 |
| 告警恢复通知 | SendResolved 开关 | 站内通知有恢复；webhook 有 | 已实现 |
