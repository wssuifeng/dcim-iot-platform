## 1. 文档定位与反推方法

- **上游锚点**：`10_系统定义/系统定义.md` v1.1（v1 于 2026-09-04 冻结；2026-09-06 升 v1.1 吸收 G-014 采纳裁决，C1–C15 + 非目标 13 项）——需求条目唯一合法性上游；本文档不新增、不修改任何 Cx 定义。
- **反推证据源**（存量项目模式二：从既有实现反推，经用户审查）：
  - 后端：`src/main/java/com/example/platform/controller/`（20 个控制器的 Swagger 注解，权限边界以注解为准）、`ingest/`（四通道契约实现）、`service/`（状态机与评估链）、`task/`（7 个定时任务）；
  - 仿真服务：`simulator/` 子项目（C12 证据，独立进程独立构建）；
  - 前端：`frontend/src/router/index.js`（页面清单 + 角色可见性）与 15 个视图目录；
  - 契约：`README.md` §3 网关北向契约（与代码核对一致）；
  - 表结构：Flyway V1–V25 迁移脚本（事实来源）。
- **编号规则**：功能需求 `FR-<Cx>-<两位序号>`；缺陷修复需求 `FR-B-<三位序号>` 与自查报告 `W-<三位序号>` 一一对应。
- **覆盖性**：C1–C15 每条至少一个 FR（共 84 条）；缺陷修复需求 37 条；全部条目挂 Cx，无游离功能点。

## 5. 核心功能端到端流程

> 对应 `_中控.md` 任务 2。参与者类型约定：系统（自动）/ 定时任务 / 采集网关（北向契约视角，持机房凭证的上报方）/ 仿真网关（仿真服务内组件）/ ADMIN / OPERATOR / VIEWER。
> 三条关键流程（5.1–5.3）逐步展开，其余核心功能每条一流程（5.4）。

### 5.1 关键流程 A：数据上报四入口（C2/C3/C4）

**公共核心（数据接收门，传输无关，四入口共用）**：
① 凭证认证与机房归属校验 → ② 未知设备自动注册（开启时，见 5.3）→ ③ 幂等去重 → ④ 采样落库（月分区，逐条独立事务）→ ⑤ 告警评估与通知分发（提交后异步，见 5.2）。

**入口 1 · HTTP HMAC 通道（C2）**
- 触发：采集网关按周期/死区/越限策略北向上报（批量 ≤200）。
- 参与者：采集网关 → GatewayAuthenticationFilter → 公共核心。
- 数据流向：`POST /api/ingest/samples`（请求头 `Authorization: Gateway {AK}:{sha256(SK+rawBody)}`）→ 验签（非法签名 100% 拒绝）→ 公共核心 → 同步返回逐条结果（成功/判重/失败明细）。
- 边界：sampleTime 晚于平台时间 +5 分钟拒绝；早于按断网补传合法接收。

**入口 2 · MQTT HMAC 通道（C2）**
- 触发：采集网关定时发布；或连接异常由 broker 代发遗嘱（LWT）。
- 参与者：采集网关 → mosquitto（dynamic-security 连接鉴权）→ IngestMqttListener → 公共核心。
- 数据流向：发布 `dcim/{accessKey}/samples`（QoS 1，报文 `{signature,batch}`）→ 验签 → 公共核心；QoS1 重发/断网补传由幂等键保证零重复；LWT 走 `dcim/{accessKey}/lwt` 直入网关离线链路（5.4-C9）。

**入口 3 · TB 兼容遥测开放通道（C3）**
- 触发：TB 生态组件/SDK 上报遥测。
- 参与者：TB 组件 → TelemetryCompatController →（映射回退）→ 公共核心。
- 数据流向：`POST /api/v1/{token}/telemetry`（token 鉴权，无逐请求签名）→ 四报文形态解析（T1 简单对象 / T2 时间戳对象 / T3 数组 / E1 `device` 多子设备扩展）→ 标准解析失败回退机房映射模板（见 5.4-C4）→ 公共核心；无 seq，幂等键降级 `deviceCode+pointCode+sampleTime`。

**入口 4 · MQTT 子凭证开放通道（C3）**
- 触发：生态组件发布报文。
- 参与者：组件 → mosquitto（连接层账号密码鉴权）→ IngestMqttListener → 公共核心。
- 数据流向：发布 `dcim-open/{mqttUsername}/samples` → 标准解析失败回退映射模板（5.4-C4）→ 公共核心。

### 5.2 关键流程 B：告警状态机与通知（C7/C8）

- 触发：采样落库提交后触发模版规则评估（生效模版 = 设备绑定优先，为空降级类型基础模版）。
- 参与者：系统（评估/状态机/通知分发）、ADMIN/OPERATOR（处理动作）、各通知渠道。
- 数据流向（主路径）：
  ① 评估命中阈值 → 多条规则取最严重级别（数字小 = 更紧急）→ 生成告警事件 **TRIGGERED**（落库 + 流转留痕）；
  ② 异步分发通知：站内（铃铛 + 模态框）/ WebSocket 弹窗 / 邮件 / IM webhook——级别过滤、失败重试、日志留痕、去重合并（5.4-C8）；下行动作 webhook 仅挂升级分支（见下）；
  ③ 人工 **ACKED**（acknowledge，附备注）→ 人工 **HANDLING**（startHandling，附备注）；
  ④ 恢复 **RECOVERED**（三路径）：a) 评估链回归确认——回到安全区且在恢复确认窗口（quiet-window-sec，默认 300s）内持续无越限；b) 停报超窗确认——定时任务扫描"最新采样回到安全区且距今超过 quiet-window-sec"；c) 人工 recover（附备注）；网关/设备离线类型由恢复采样/心跳自动 autoRecover（"从未上线"凭证场景恢复缺陷见 FR-B-030）；
  ⑤ 人工 **CLOSED**（close，附备注）→ 归档。
- 分支：**级别升级**——活动期间命中更严重级别 → ALARM_UPGRADED（升级留痕 + 机房可配下行动作 webhook）；**逻辑删除**——事件可逻辑删除，流转与处理记录全程可查。
- 留痕证据：alarm_state_transition / alarm_handling_record 全程记录操作者与备注；实测时效（含网关上报周期的端到端抽检）：注入 +60kW 突升 → 2 分钟内 METRIC 告警并自动恢复（压测报告 §5 抽检；落库时效判据另见 NFR-05）。

### 5.3 关键流程 C：首包自动注册（C5）

- 触发：未知 deviceCode 首次上报采样，且该凭证自动注册开启。
- 参与者：采集网关 → 公共核心② → DeviceTypeInferencer → 设备/类型/模版模型。
- 数据流向：① 机房归属校验通过 → ② 未知 deviceCode 触发自动建档（deviceCode 全局寻址）→ ③ 按上报指标编码推断类型（如 temperature → 温湿度）→ ④ 类型基础告警模版与类型级指标模板自动绑定（零配置跟随）→ ⑤ 本采样继续走幂等去重 → 落库 → 评估；后续上报按已知设备直入核心链。
- 开关：凭证维度可关闭自动注册，关闭后未知设备不触发建档。
