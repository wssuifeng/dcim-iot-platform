# 第一章 概念引入——从设备管理到智能监控

## 1.1 设备管理 vs 智能监控的差距

在第五周，我们完成了设备管理模块——有了完整的 CRUD 接口、请求校验、异常处理、分页查询和 CORS 配置。但这个系统还**不能感知数据变化**，因为：

| 对比维度 | 设备管理状态（第五周结束）  | 智能监控目标（第六周目标）  |
| ---- | :------------- | :------------- |
| 数据采集 | 无——设备数据表存在但无接口 | 完整的数据上报与存储接口   |
| 告警检测 | 无——告警表存在但无触发机制 | 基于阈值的自动告警触发    |
| 告警处理 | 无——告警状态无法变更    | 完整的告警确认与处理流程   |
| 数据分析 | 无——仅能查看原始数据    | 趋势分析、聚合统计、状态概览 |
| 定时检查 | 无——依赖手动触发      | 定时扫描异常数据       |

> **💡 类比理解**：设备管理就像给每台设备发了"身份证"，但系统还是"聋子"——设备在疯狂上报数据，系统听不到；设备出了问题，系统看不到。本周要做的就是给系统装上"耳朵"（数据采集）和"大脑"（告警检测），让它能听懂设备在说什么，并在出问题时主动报警。

### 3.1.1 基础概念：物联网数据采集流程

#### 数据采集的核心概念

**物联网数据采集**是指设备端通过传感器获取环境数据（温度、湿度、烟雾浓度等），并通过网络上报到平台进行存储和分析的过程。

```
传感器采集数据 → 设备端封装JSON → HTTP POST上报 → 后端接收存储 → 数据分析/告警
```

| 概念   | 说明             | 本项目实现                              |
| ---- | -------------- | ---------------------------------- |
| 数据上报 | 设备向平台提交采集数据    | `POST /api/device-data`            |
| 数据存储 | 将上报数据持久化到数据库   | `device_data` 表                    |
| 数据查询 | 按设备、时间范围查询历史数据 | `GET /api/device-data/device/{id}` |
| 数据统计 | 聚合分析数据趋势       | `GET /api/device-data/statistics`  |

#### 核心技术：数据上报接口设计

设备数据上报接口需要考虑以下关键点：

| 设计要点  | 说明               | 实现方式                  |
| ----- | ---------------- | --------------------- |
| 数据校验  | 上报数据必须包含设备ID和数据值 | `@Valid` + `@NotNull` |
| 设备存在性 | 上报数据的设备必须存在      | Service 层校验           |
| 时间戳   | 采集时间由设备端或服务端提供   | 优先使用设备端时间             |
| 批量上报  | 支持一次上报多条数据       | 批量插入接口                |

> **🔍 深入理解**：为什么数据校验要分两层？
>
> - **第一层（@Valid 注解）**：校验请求格式是否正确（字段是否为空、长度是否合规），这是"语法校验"
> - **第二层（Service 层）**：校验业务逻辑是否正确（设备是否存在、数据值是否在合理范围），这是"语义校验"
> - 面试中常问："参数校验应该在哪一层做？"——答案是**两层都要做**，Controller 层做格式校验，Service 层做业务校验。

### 3.1.2 核心技术：Entity 实体类完整定义

在编写 Controller 之前，必须先确保 Entity 类定义完整且包含校验注解。这是很多新手容易忽略的步骤。

**▶ 任务要求**

- 完善 `DeviceData` 实体类，添加校验注解
- 完善 `Alert` 实体类，添加校验注解
- 在 `DeviceService` 中添加 `getDeviceOrThrow` 辅助方法

**📁 文件路径：src/main/java/com/example/platform/entity/DeviceData.java**

```java
package com.example.platform.entity;

import com.baomidou.mybatisplus.annotation.*;
import jakarta.validation.constraints.DecimalMax;
import jakarta.validation.constraints.DecimalMin;
import jakarta.validation.constraints.NotNull;
import lombok.Data;

import java.io.Serial;
import java.io.Serializable;
import java.math.BigDecimal;
import java.time.LocalDateTime;

@Data
@TableName("device_data")
public class DeviceData implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;

    /** 数据ID（主键，BIGINT 类型） */
    @TableId(value = "id", type = IdType.AUTO)
    private Long id;

    /** 设备ID（关联 devices 表） */
    @TableField("device_id")
    @NotNull(message = "设备ID不能为空")
    private Integer deviceId;

    /** 数据指标标识（如 temperature、humidity），替代原 dataUnit */
    @TableField("metric")
    private String metric;

    /** 数据值（保留两位小数） */
    @NotNull(message = "数据值不能为空")
    @DecimalMin(value = "-999.99", message = "数据值不能小于-999.99")
    @DecimalMax(value = "999.99", message = "数据值不能超过999.99")
    @TableField("data_value")
    private BigDecimal dataValue;

    /** 采集时间（由 MyMetaObjectHandler 自动填充） */
    @TableField(value = "collect_time", fill = FieldFill.INSERT)
    private LocalDateTime collectTime;
}
```

> **⚠️ 关键变更说明**（相比文档 v3.1）：
>
> - `id` 类型从 `Integer` 改为 `Long`，对应数据库 BIGINT 主键
> - **新增** **`metric`** **字段**替代原 `dataUnit`：`metric` 存储指标标识（如 `temperature`），通过 `DictMetricService` 缓存获取中文单位，实现指标与单位的解耦
> - `collectTime` 添加 `fill = FieldFill.INSERT`，由 `MyMetaObjectHandler` 自动填充当前时间，前端不传则自动补全
> - 新增 `@TableField` 注解显式映射数据库字段名

**📁 文件路径：src/main/java/com/example/platform/entity/Alert.java**

```java
package com.example.platform.entity;

import com.baomidou.mybatisplus.annotation.*;
import lombok.Data;

import java.io.Serial;
import java.io.Serializable;
import java.time.LocalDateTime;

@Data
@TableName("alerts")
public class Alert implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;

    /** 告警ID（主键，自增） */
    @TableId(value = "id", type = IdType.AUTO)
    private Integer id;

    /** 设备ID（关联 devices 表） */
    @TableField("device_id")
    private Integer deviceId;

    /** 告警类型（如"threshold"，由 AlertRuleDefinition.alertType 定义） */
    @TableField("alert_type")
    private String alertType;

    /** 告警级别：1-紧急，2-严重，3-一般，4-警告，5-提示 */
    @TableField("alert_level")
    private Integer alertLevel;

    /** 告警详细描述 */
    @TableField("alert_message")
    private String alertMessage;

    /** 是否处理：0-未处理，1-已处理 */
    @TableField("is_handled")
    private Integer isHandled;

    /** 处理时间 */
    @TableField(value = "handle_time")
    private LocalDateTime handleTime;

    /** 处理人（用户名或工号） */
    @TableField("handle_user")
    private String handleUser;

    /** 告警产生时间（由 MyMetaObjectHandler 自动填充） */
    @TableField(value = "create_time", fill = FieldFill.INSERT)
    private LocalDateTime createTime;
}
```

> **⚠️ 关键变更说明**（相比文档 v3.1）：
>
> - **告警级别从3级制改为5级制**：1-紧急(Critical)、2-严重(Major)、3-一般(Minor)、4-警告(Warning)、5-提示(Info)，与 `AlertRuleDefinition.level` 的 `@Min(1) @Max(5)` 校验一致
> - `createTime` 添加 `fill = FieldFill.INSERT`，由 `MyMetaObjectHandler` 自动填充，不再手动设置
> - `alertType` 的值由 `AlertRuleDefinition.alertType` 定义（如 `threshold`、`trend`、`absence`），而非硬编码的中文名

> **⚠️ 注意事项**：
>
> - `@NotNull` 是 Jakarta Validation 的注解，需要确保 `pom.xml` 中已引入 `spring-boot-starter-validation` 依赖
> - `@DecimalMin` 只对 BigDecimal 类型生效，如果 dataValue 是 Double 类型则无效
> - `collectTime` 不加 `@NotNull` 是因为：如果设备端未传时间，后端会自动填充当前时间

**📁 在 DeviceService 中添加 getDeviceOrThrow 方法：**

```java
@Override

    Device device = getById(id);
    if (device == null) {
        throw new DeviceNotFoundException(id);
    }
    return device;
}
```

> 2. 异常由全局异常处理器统一捕获，返回标准错误响应

```java
package com.example.platform.controller;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.example.platform.common.Result;
import com.example.platform.entity.Device;
import com.example.platform.entity.DeviceData;
import com.example.platform.service.DeviceDataService;
import com.example.platform.service.DeviceService;
import jakarta.validation.Valid;
import org.springframework.format.annotation.DateTimeFormat;
import org.springframework.web.bind.annotation.*;

import java.time.LocalDateTime;
import java.util.List;

@RestController
@RequestMapping("/device-data")
public class DeviceDataController {

    private final DeviceDataService deviceDataService;
    private final DeviceService deviceService;

    public DeviceDataController(DeviceDataService deviceDataService,
                                DeviceService deviceService) {
        this.deviceDataService = deviceDataService;
        this.deviceService = deviceService;
    }

    @PostMapping
    public Result<Void> reportData(@Valid @RequestBody DeviceData deviceData) {
        deviceDataService.saveWithAlertCheck(deviceData);
        return Result.success();
    }

    @PostMapping("/batch")
    public Result<Void> reportBatch(@Valid @RequestBody DeviceDataBatchDTO batchDTO) {
        List<DeviceData> dataList = batchDTO.getDataList();
        for (DeviceData data : dataList) {
            deviceDataService.saveWithAlertCheck(data);
        }
        return Result.success();
    }

    @GetMapping("/device/{deviceId}")
    public Result<Page<DeviceData>> listByDevice(
            @PathVariable Integer deviceId,
            @RequestParam(defaultValue = "1") Integer current,
            @RequestParam(defaultValue = "20") Integer size) {
        deviceService.getDeviceOrThrow(deviceId);
        Page<DeviceData> page = new Page<>(current, size);
        LambdaQueryWrapper<DeviceData> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(DeviceData::getDeviceId, deviceId)
               .orderByDesc(DeviceData::getCollectTime);
        return Result.success(deviceDataService.page(page, wrapper));
    }

    @GetMapping("/device/{deviceId}/latest")
    public Result<DeviceData> getLatest(@PathVariable Integer deviceId) {
        deviceService.getDeviceOrThrow(deviceId);
        DeviceData latest = deviceDataService.findLatestByDeviceId(deviceId);
        if (latest == null) {
            return Result.error(404, "该设备暂无采集数据");
        }
        return Result.success(latest);
    }

    @GetMapping("/device/{deviceId}/range")
    public Result<List<DeviceData>> listByTimeRange(
            @PathVariable Integer deviceId,
            @RequestParam @DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss") LocalDateTime startTime,
            @RequestParam @DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss") LocalDateTime endTime) {
        deviceService.getDeviceOrThrow(deviceId);
        List<DeviceData> list = deviceDataService.findByDeviceIdAndTimeRange(
                deviceId, startTime, endTime);
        return Result.success(list);
    }

    @GetMapping("/device/{deviceId}/statistics")
    public Result<java.util.Map<String, Object>> getStatistics(
            @PathVariable Integer deviceId,
            @RequestParam @DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss") LocalDateTime startTime,
            @RequestParam @DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss") LocalDateTime endTime) {
        deviceService.getDeviceOrThrow(deviceId);
        java.util.Map<String, Object> stats = deviceDataService.getStatistics(
                deviceId, startTime, endTime);
        return Result.success(stats);
    }

    @GetMapping("/page")
    public Result<Page<DeviceData>> listByPage(
            @RequestParam(defaultValue = "1") Integer current,
            @RequestParam(defaultValue = "10") Integer size,
            @RequestParam(required = false) Integer deviceId) {
        Page<DeviceData> page = new Page<>(current, size);
        LambdaQueryWrapper<DeviceData> wrapper = new LambdaQueryWrapper<>();
        if (deviceId != null) {
            wrapper.eq(DeviceData::getDeviceId, deviceId);
        }
        wrapper.orderByDesc(DeviceData::getCollectTime);
        Page<DeviceData> result = deviceDataService.page(page, wrapper);
        return Result.success(result);
    }
}
```

> **⚠️ 关键设计说明**：`reportData` 方法调用的是 `deviceDataService.saveWithAlertCheck(deviceData)`，而非直接调用 `save()`。这是因为数据保存和告警检测必须在**同一个事务**中完成（详见 Day 2 的 AlertRuleEngine 集成）。如果先 `save()` 再 `evaluate()`，当告警创建失败时，已保存的数据不会回滚，导致数据不一致。

```java
package com.example.platform.service.impl;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.extension.service.impl.ServiceImpl;
import com.example.platform.entity.Device;
import com.example.platform.entity.DeviceData;
import com.example.platform.mapper.DeviceDataMapper;
import com.example.platform.service.DeviceDataService;
import com.example.platform.service.DeviceService;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.LocalDateTime;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

@Service
public class DeviceDataServiceImpl extends ServiceImpl<DeviceDataMapper, DeviceData>
        implements DeviceDataService {

    private final AlertRuleEngine alertRuleEngine;
    private final DeviceService deviceService;

    public DeviceDataServiceImpl(AlertRuleEngine alertRuleEngine,
                                  DeviceService deviceService) {
        this.alertRuleEngine = alertRuleEngine;
        this.deviceService = deviceService;
    }

    @Override
    public List<DeviceData> findByDeviceId(Integer deviceId) {
        LambdaQueryWrapper<DeviceData> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(DeviceData::getDeviceId, deviceId)
               .orderByDesc(DeviceData::getCollectTime);
        return list(wrapper);
    }

    @Override
    public DeviceData findLatestByDeviceId(Integer deviceId) {
        LambdaQueryWrapper<DeviceData> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(DeviceData::getDeviceId, deviceId)
               .orderByDesc(DeviceData::getCollectTime)
               .last("LIMIT 1");
        return getOne(wrapper);
    }

    @Override
    public List<DeviceData> findByDeviceIdAndTimeRange(Integer deviceId,
            LocalDateTime startTime, LocalDateTime endTime) {
        LambdaQueryWrapper<DeviceData> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(DeviceData::getDeviceId, deviceId)
               .between(DeviceData::getCollectTime, startTime, endTime)
               .orderByAsc(DeviceData::getCollectTime);
        return list(wrapper);
    }

    @Override
    public Map<String, Object> getStatistics(Integer deviceId,
            LocalDateTime startTime, LocalDateTime endTime) {
        Map<String, Object> stats = baseMapper.getStatisticsByDeviceIdAndTimeRange(
                deviceId, startTime, endTime);
        if (stats == null) {
            stats = new HashMap<>();
            stats.put("deviceId", deviceId);
            stats.put("count", 0);
            stats.put("minVal", null);
            stats.put("maxVal", null);
            stats.put("avgVal", null);
        }
        return stats;
    }

    @Transactional(rollbackFor = Exception.class)
    @Override
    public void saveWithAlertCheck(DeviceData deviceData) {
        // 1. 校验设备存在（同时取出设备信息供告警引擎使用）
        deviceService.getDeviceOrThrow(deviceData.getDeviceId());

        // 2. 保存数据（collectTime 由 MyMetaObjectHandler 自动填充）
        save(deviceData);

        // 3. 触发告警规则评估
        alertRuleEngine.evaluate(deviceData.getDeviceId(), deviceData);
    }
}
```

> **⚠️ 关键变更说明**（相比文档 v3.1）：
>
> - **删除了手动设置时间戳的代码**：`collectTime` 由 `MyMetaObjectHandler.insertFill()` 自动填充，`createTime` 同理，无需在 Service 层手动设置
> - **`evaluate`** **方法从3个参数改为2个参数**：原 `evaluate(deviceId, typeId, data)` → 现 `evaluate(deviceId, data)`，引擎内部自行获取设备类型信息
> - 这种设计使 `DeviceDataServiceImpl` 不再需要关心告警引擎的内部逻辑，降低了耦合度

> **🔍 深入理解——@Transactional 的 rollbackFor 参数**：
>
> - 默认情况下，`@Transactional` 只对 `RuntimeException` 和 `Error` 回滚
> - `rollbackFor = Exception.class` 表示**所有异常都回滚**，包括受检异常（checked exception）
> - 面试高频问题：**"@Transactional 默认回滚什么异常？如何修改？"**
>   - 答：默认只回滚 `RuntimeException` 和 `Error`，通过 `rollbackFor` 可扩展到所有异常

### 3.2.1 基础概念：告警规则引擎

#### 什么是告警规则引擎？

**告警规则引擎**是物联网平台的核心组件，负责监控设备数据，当数据满足预设条件时自动触发告警。它将"数据检测逻辑"与"业务处理逻辑"解耦，使得告警规则可以灵活配置和扩展。

| 概念    | 说明          | 本项目实现                                                           |
| ----- | ----------- | --------------------------------------------------------------- |
| 告警规则  | 定义什么条件下触发告警 | `AlertRuleConfig` + `AlertRuleDefinition`（配置化规则，JSON 存储）        |
| 规则引擎  | 执行规则检测的核心组件 | `AlertRuleEngine`（配置化评估，非硬编码阈值）                                 |
| 告警类型  | 告警的分类       | 由 `AlertRuleDefinition.alertType` 定义（如 threshold、trend、absence） |
| 告警级别  | 告警的严重程度     | 1-紧急、2-严重、3-一般、4-警告、5-提示（5级制）                                   |
| 规则优先级 | 设备级优先，类型级降级 | 设备自身配置 > 设备类型默认配置                                               |

#### 核心技术：从硬编码到配置化规则引擎

**策略模式**定义了一系列算法，将每个算法封装起来，并使它们可以互相替换。在当前项目中，我们采用**配置化规则**方案替代了传统的策略模式：

```
AlertRuleEngine（统一评估引擎）
    ├── 读取 AlertRuleConfig（设备级优先 → 类型级降级）
    ├── 过滤匹配指标的规则（按 metric 字段匹配）
    ├── 按告警类型分组遍历评估（evaluateRule 方法统一比较）
    ├── 防重与升级（activeAlertMap 快照 + 级别比较）
    └── 批量保存新告警（saveBatch）
```

| 设计方案           | 适用场景            | 本项目选择                                    |
| -------------- | --------------- | ---------------------------------------- |
| 策略模式 + switch  | 规则类型少且固定（3-5种）  | ❌ 已弃用：硬编码阈值无法动态配置                        |
| 配置化规则引擎        | 规则需要动态配置、设备级差异化 | ✅ 当前方案：`AlertRuleConfig` JSON 存储，支持运行时修改 |
| 规则引擎框架（Drools） | 复杂业务规则、大量规则组合   | 🔮 未来扩展：当规则复杂度超过配置化方案时引入                 |

> **🔍 深入理解——为什么从 switch + 硬编码阈值改为配置化规则？**
>
> - **原方案缺陷**：阈值写死在代码中（`TEMP_HIGH_THRESHOLD = 80`），修改阈值需要改代码重新部署
> - **配置化优势**：规则存储在数据库 `alert_rule_config` 字段中（JSON 格式），通过 API 即可修改，无需重新部署
> - **设备级差异化**：不同设备可以配置不同的告警规则（如实验室温度阈值 80℃，仓库阈值 40℃）
> - **面试回答**："简单场景用 switch 就够了；当规则需要动态配置或设备级差异化时，用配置化规则引擎更合适。"

### 3.2.2 核心技术：AlertRuleEngine 实现

**▶ 任务要求**

- 创建 `AlertRuleEngine` 配置化告警规则引擎
- 实现设备级优先、类型级降级的规则获取策略
- 实现基于 `AlertRuleDefinition` 的通用阈值评估

- 实现告警消息的模板化生成（含指标字典降级）

**📁 文件路径：src/main/java/com/example/platform/service/impl/AlertRuleEngine.java**

```java
package com.example.platform.service.impl;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.core.conditions.update.LambdaUpdateWrapper;
import com.example.platform.dto.AlertRuleConfig;
import com.example.platform.dto.AlertRuleDefinition;
import com.example.platform.entity.Alert;
import com.example.platform.entity.Device;
import com.example.platform.entity.DeviceData;
import com.example.platform.entity.DeviceType;
import com.example.platform.entity.DictMetric;
import com.example.platform.service.AlertService;
import com.example.platform.service.DeviceService;
import com.example.platform.service.DeviceTypeService;
import com.example.platform.service.DictMetricService;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;

import java.math.BigDecimal;
import java.util.*;
import java.util.stream.Collectors;

@Slf4j
@Component
public class AlertRuleEngine {

    private final AlertService alertService;
    private final DeviceService deviceService;
    private final DeviceTypeService deviceTypeService;
    private final DictMetricService dictMetricService;

    public AlertRuleEngine(AlertService alertService, DeviceService deviceService,
                           DeviceTypeService deviceTypeService, DictMetricService dictMetricService) {
        this.alertService = alertService;
        this.deviceService = deviceService;
        this.deviceTypeService = deviceTypeService;
        this.dictMetricService = dictMetricService;
    }

    /**
     * 评估设备数据是否触发告警
     */
    public void evaluate(Integer deviceId, DeviceData data) {

        // ===== 1. 基础校验 =====
        BigDecimal value = data.getDataValue();
        if (value == null) {
            return;
        }
        Device device = deviceService.getDeviceOrThrow(deviceId);

        // ===== 2. 获取规则并过滤排序 =====
        AlertRuleConfig effectiveConfig = getEffectiveRuleConfig(device);
        if (effectiveConfig == null || effectiveConfig.getRules() == null
                || effectiveConfig.getRules().isEmpty()) {
            return;
        }

        // 过滤出指标匹配的规则，按级别降序排序
        // 注意：5级制中 1=紧急(最严重) 5=提示(最轻微)
        // 降序排序使高级别编号(较轻微)的规则先评估，低级别编号(较严重)的后评估
        // 配合 break 命中即止，实际触发的是该告警类型中最轻微的匹配规则
        List<AlertRuleDefinition> sortedMatchedRules = effectiveConfig.getRules().stream()
                .filter(rule -> isMetricMatched(rule, data))
                .sorted(Comparator.comparingInt(AlertRuleDefinition::getLevel).reversed())
                .toList();

        if (sortedMatchedRules.isEmpty()) {
            return;
        }

        // ===== 3. 获取当前设备的活跃告警快照（避免 N+1 问题） =====
        Map<String, Alert> activeAlertMap = getActiveAlertMap(deviceId);

        // ===== 4. 按告警类型分组遍历评估 =====
        Map<String, List<AlertRuleDefinition>> groupedRules = sortedMatchedRules.stream()
                .collect(Collectors.groupingBy(
                        rule -> StringUtils.hasText(rule.getAlertType())
                                ? rule.getAlertType() : "DEFAULT_TYPE"));

        List<Alert> pendingAlerts = new ArrayList<>();

        for (Map.Entry<String, List<AlertRuleDefinition>> entry : groupedRules.entrySet()) {
            String alertType = entry.getKey();
            List<AlertRuleDefinition> rulesOfType = entry.getValue();

            for (AlertRuleDefinition rule : rulesOfType) {
                if (evaluateRule(value, rule)) {
                    Alert existingAlert = activeAlertMap.get(alertType);

                    if (existingAlert == null) {
                        // 没有活跃告警，准备新增一条
                        pendingAlerts.add(buildAlertEntity(deviceId, rule, value));
                    } else {
                        // 已有活跃告警，如果新触发的规则级别更高，则升级现有告警
                        if (rule.getLevel() > existingAlert.getAlertLevel()) {
                            upgradeAlert(existingAlert.getId(), rule, value);
                        }
                    }
                    // 命中即止
                    break;
                }
            }
        }

        // ===== 5. 批量保存 =====
        if (!pendingAlerts.isEmpty()) {
            alertService.saveBatch(pendingAlerts);
            log.info("🚨 批量新增告警：deviceId={}, 数量={}", deviceId, pendingAlerts.size());
        }
    }

    // ==================== 私有辅助方法 ====================

    /** 一次性查出该设备所有未处理告警，转成 Map 方便按 alertType 快速查找 */
    private Map<String, Alert> getActiveAlertMap(Integer deviceId) {
        List<Alert> activeAlerts = alertService.list(
                new LambdaQueryWrapper<Alert>()
                        .eq(Alert::getDeviceId, deviceId)
                        .eq(Alert::getIsHandled, 0)
        );
        if (activeAlerts == null || activeAlerts.isEmpty()) {
            return Collections.emptyMap();
        }
        return activeAlerts.stream()
                .collect(Collectors.toMap(Alert::getAlertType,
                        alert -> alert, (existing, replacement) -> existing));
    }

    /** 获取生效规则（设备自己配的优先，没配就用设备类型的） */
    private AlertRuleConfig getEffectiveRuleConfig(Device device) {
        if (device.getAlertRuleConfig() != null
                && !device.getAlertRuleConfig().getRules().isEmpty()) {
            return device.getAlertRuleConfig();
        }
        DeviceType type = deviceTypeService.getById(device.getTypeId());
        if (type != null && type.getAlertRuleConfig() != null
                && !type.getAlertRuleConfig().getRules().isEmpty()) {
            return type.getAlertRuleConfig();
        }
        return null;
    }

    /** 判断数据指标是否匹配规则 */
    private boolean isMetricMatched(AlertRuleDefinition rule, DeviceData data) {
        if (!StringUtils.hasText(rule.getMetric())) return true;
        if (!StringUtils.hasText(data.getMetric())) return false;
        return rule.getMetric().equals(data.getMetric());
    }

    /** 比较数值是否超过阈值 */
    private boolean evaluateRule(BigDecimal value, AlertRuleDefinition rule) {
        if (rule.getThreshold() == null || !StringUtils.hasText(rule.getOperator())) return false;
        String op = rule.getOperator().trim();
        int result = value.compareTo(rule.getThreshold());
        return switch (op) {
            case ">" -> result > 0;
            case "<" -> result < 0;
            case ">=" -> result >= 0;
            case "<=" -> result <= 0;
            case "==" -> result == 0;
            default -> false;
        };
    }

    /** 组装一个新的告警实体（还没存库的） */
    private Alert buildAlertEntity(Integer deviceId, AlertRuleDefinition rule,
                                   BigDecimal value) {
        Alert alert = new Alert();
        alert.setDeviceId(deviceId);
        alert.setAlertType(rule.getAlertType());
        alert.setAlertLevel(rule.getLevel());
        alert.setAlertMessage(buildAlertMessage(rule, value));
        alert.setIsHandled(0);
        return alert;
    }

    /** 升级告警：直接更新数据库里的告警级别和消息内容 */
    private void upgradeAlert(Integer existingAlertId, AlertRuleDefinition newRule,
                              BigDecimal value) {
        LambdaUpdateWrapper<Alert> updateWrapper = new LambdaUpdateWrapper<>();
        updateWrapper.eq(Alert::getId, existingAlertId)
                .set(Alert::getAlertLevel, newRule.getLevel())
                .set(Alert::getAlertMessage, buildAlertMessage(newRule, value));
        alertService.update(updateWrapper);
        log.info("⬆️ 告警升级：alertId={}, 升级为 {}级", existingAlertId, newRule.getLevel());
    }

    /** 生成告警消息，自动从字典服务拿中文指标名和单位 */
    private String buildAlertMessage(AlertRuleDefinition rule, BigDecimal value) {
        DictMetric metricInfo = dictMetricService.getFromCache(rule.getMetric());

        String metricName = (metricInfo != null
                && StringUtils.hasText(metricInfo.getMetricName()))
                ? metricInfo.getMetricName()
                : (StringUtils.hasText(rule.getMetric()) ? rule.getMetric() : "未知指标");

        String metricUnit = (metricInfo != null
                && StringUtils.hasText(metricInfo.getMetricUnit()))
                ? metricInfo.getMetricUnit() : "";

        if (StringUtils.hasText(rule.getMessageTemplate())) {
            return rule.getMessageTemplate()
                    .replace("{metricName}", metricName)
                    .replace("{unit}", metricUnit)
                    .replace("{value}", value.toString())
                    .replace("{threshold}", rule.getThreshold().toString());
        }

        return String.format("%s 触发规则，当前值 %s%s，阈值 %s %s%s",
                metricName, value, metricUnit,
                rule.getOperator(), rule.getThreshold(), metricUnit);
    }
}
```

### 3.3.1 基础概念：告警状态机

#### 告警状态流转

告警从产生到关闭，经历以下状态流转：

```
┌──────────┐    确认处理     ┌──────────┐
│  未处理   │ ─────────────→ │  已处理   │
│ (isHandled=0) │              │ (isHandled=1) │
└──────────┘                └──────────┘
     │                           │
     │ 忽略（直接关闭）            │ 重新打开
     └──────────→ 已处理 ←───────┘
```

| 状态值 | 状态名称 | 允许操作    | 说明       |
| --- | ---- | ------- | -------- |
| 0   | 未处理  | 确认处理、忽略 | 新产生的告警   |
| 1   | 已处理  | 重新打开    | 已确认并处理完毕 |

> **💡 实战贴士**：当前项目使用简化的两态模型（未处理/已处理），足以满足实习项目需求。实际企业项目中可能需要更多状态（如处理中、已委派、已关闭等），这时就需要更完整的状态机设计。

```java
package com.example.platform.service.impl;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.extension.service.impl.ServiceImpl;
import com.example.platform.entity.Alert;
import com.example.platform.mapper.AlertMapper;
import com.example.platform.service.AlertService;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.LocalDateTime;
import java.util.List;

@Service
public class AlertServiceImpl extends ServiceImpl<AlertMapper, Alert>
        implements AlertService {

    @Override
    public List<Alert> findUnhandled() {
        LambdaQueryWrapper<Alert> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(Alert::getIsHandled, 0)
               .orderByDesc(Alert::getAlertLevel)
               .orderByDesc(Alert::getCreateTime);
        return list(wrapper);
    }

    @Override
    public List<Alert> findByDeviceId(Integer deviceId) {
        LambdaQueryWrapper<Alert> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(Alert::getDeviceId, deviceId)
               .orderByDesc(Alert::getCreateTime);
        return list(wrapper);
    }

    @Transactional(rollbackFor = Exception.class)
    @Override
    public int batchHandle(List<Integer> ids, String handleUser) {
        LambdaUpdateWrapper<Alert> wrapper = new LambdaUpdateWrapper<>();
        wrapper.in(Alert::getId, ids)
               .eq(Alert::getIsHandled, 0)
               .set(Alert::getIsHandled, 1)
               .set(Alert::getHandleTime, LocalDateTime.now())
               .set(Alert::getHandleUser, handleUser);
        return baseMapper.update(null, wrapper);
    }
}
```

>
> | 方案    | 实现方式                            | 适用场景         |

> | 乐观锁   | 添加 `version` 字段 + `@Version` 注解 | 低并发场景（本项目推荐） |
> | 悲观锁   | `SELECT ... FOR UPDATE`         | 高并发场景        |
> | 数据库约束 | 唌一约束 + 状态校验                     | 简单场景         |
>

### 3.4.1 基础概念：数据统计与聚合查询

#### 聚合查询的核心概念

**聚合查询**是对一组数据进行计算并返回单个值的查询方式，常用于统计分析。

| 聚合函数       | 作用    | 示例                                                                      |
| ---------- | ----- | ----------------------------------------------------------------------- |
| `COUNT()`  | 统计记录数 | `SELECT COUNT(*) FROM device_data`                                      |
| `SUM()`    | 求和    | `SELECT SUM(data_value) FROM device_data`                               |
| `AVG()`    | 求平均值  | `SELECT AVG(data_value) FROM device_data`                               |
| `MAX()`    | 求最大值  | `SELECT MAX(data_value) FROM device_data`                               |
| `MIN()`    | 求最小值  | `SELECT MIN(data_value) FROM device_data`                               |
| `GROUP BY` | 分组聚合  | `SELECT device_id, AVG(data_value) FROM device_data GROUP BY device_id` |

> **🔍 深入理解——聚合查询的性能陷阱**：
>
> - **全表扫描**：没有索引的聚合查询会扫描整张表，百万级数据可能需要数秒
> - **临时表排序**：`GROUP BY` + `ORDER BY` 可能产生临时表和文件排序
> - **优化建议**：① 聚合字段建索引 ② 限制时间范围 ③ 考虑预计算（定时统计写入汇总表）

### 3.4.3 实践应用：定时任务实现设备离线检测

**▶ 任务要求**

- 创建 `DeviceMonitorTask` 定时任务类
- 使用 `@Scheduled` 实现定时设备状态检查
- 检测超过指定时间未上线的设备并产生告警
- 避免重复告警

**📁 文件路径：src/main/java/com/example/platform/task/DeviceMonitorTask.java**

```java
package com.example.platform.task;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.example.platform.entity.Alert;
import com.example.platform.entity.Device;
import com.example.platform.service.AlertService;
import com.example.platform.service.DeviceService;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.List;

@Component
public class DeviceMonitorTask {

    private static final Logger log = LoggerFactory.getLogger(DeviceMonitorTask.class);
    private static final int OFFLINE_THRESHOLD_MINUTES = 30;

    private final DeviceService deviceService;
    private final AlertService alertService;

    public DeviceMonitorTask(DeviceService deviceService,
                              AlertService alertService) {
        this.deviceService = deviceService;
        this.alertService = alertService;
    }

    @Scheduled(fixedRate = 300000)
    public void checkDeviceOnlineStatus() {
        log.info("开始检查设备在线状态...");

        LocalDateTime threshold = LocalDateTime.now()
                .minusMinutes(OFFLINE_THRESHOLD_MINUTES);

        LambdaQueryWrapper<Device> wrapper = new LambdaQueryWrapper<>();
        wrapper.eq(Device::getStatus, 1)
               .lt(Device::getLastOnlineTime, threshold);

        List<Device> offlineDevices = deviceService.list(wrapper);

        for (Device device : offlineDevices) {
            boolean alreadyAlerted = alertService.count(
                    new LambdaQueryWrapper<Alert>()
                            .eq(Alert::getDeviceId, device.getId())
                            .eq(Alert::getAlertType, "设备离线")
                            .eq(Alert::getIsHandled, 0)
            ) > 0;

            if (!alreadyAlerted) {
                Alert alert = new Alert();
                alert.setDeviceId(device.getId());
                alert.setAlertType("设备离线");
                alert.setAlertLevel(2);
                alert.setAlertMessage("设备 [" + device.getDeviceName() +
                        "] 已超过 " + OFFLINE_THRESHOLD_MINUTES +
                        " 分钟未上报数据，可能已离线");
                alert.setIsHandled(0);
                alertService.save(alert);
                log.warn("设备离线告警：{}", device.getDeviceName());
            }
        }

        log.info("设备在线状态检查完成，发现 {} 台设备可能离线",
                offlineDevices.size());
    }
}
```

> **⚠️ 重要**：使用 `@Scheduled` 需要在启动类上添加 `@EnableScheduling` 注解：

```java
@SpringBootApplication
@MapperScan("com.example.platform.mapper")
@EnableScheduling
public class IotPlatformApplication {
    public static void main(String[] args) {
        SpringApplication.run(IotPlatformApplication.class, args);
    }
}
```

> **⚠️ 定时任务的注意事项**：
>
> 1. **`fixedRate`** **vs** **`fixedDelay`**：`fixedRate` 从上次**开始**时间算间隔，`fixedDelay` 从上次**结束**时间算间隔。如果任务执行耗时3分钟，`fixedRate=5min` 实际间隔只有2分钟
> 2. **单线程执行**：默认所有 `@Scheduled` 方法共用一个线程，一个任务阻塞会影响其他任务。解决方案：配置线程池
> 3. **集群重复执行**：多实例部署时，每个实例都会执行定时任务。解决方案：分布式锁（Redis）或只在一个实例上启用
> 4. **异常处理**：定时任务中的异常不会中断调度，但本次执行会静默失败。务必加 try-catch

> **❓ 常见错误**：定时任务不执行——检查清单：
>
> - [ ] 启动类是否添加了 `@EnableScheduling`
> - [ ] 任务类是否添加了 `@Component`
> - [ ] 方法是否添加了 `@Scheduled`
> - [ ] 方法是否是 `public void` 且无参数
> - [ ] 是否被 `@Profile` 条件注解排除了

```java
public void evaluate(Integer deviceId, DeviceData data) {
    // 1. 获取设备信息
    Device device = deviceService.getDeviceOrThrow(deviceId);
    // 2. 获取生效规则（设备级优先，类型级降级）
    AlertRuleConfig effectiveConfig = getEffectiveRuleConfig(device);
    // 3. 过滤匹配指标的规则（metric = "temperature"）
    List<AlertRuleDefinition> sortedMatchedRules = effectiveConfig.getRules().stream()
            .filter(rule -> isMetricMatched(rule, data))
            .sorted(Comparator.comparingInt(AlertRuleDefinition::getLevel).reversed())
            .toList();
    // 4. 获取活跃告警快照
    Map<String, Alert> activeAlertMap = getActiveAlertMap(deviceId);
    // 5. 评估规则：85.6 > 80 → 触发
    for (AlertRuleDefinition rule : sortedMatchedRules) {
        if (evaluateRule(value, rule)) {  // 85.6 > 80 → true
            // 6. 无活跃告警 → 新增
            pendingAlerts.add(buildAlertEntity(deviceId, rule, value));
            break;  // 命中即止
        }
    }
    // 7. 批量保存
    alertService.saveBatch(pendingAlerts);
}
```

**步骤5：告警记录自动创建，事务提交**

数据库 `alerts` 表新增一条记录：

| 字段             | 值                                                    |
| -------------- | ---------------------------------------------------- |
| device\_id     | 1                                                    |
| alert\_type    | threshold（由 AlertRuleDefinition.alertType 定义）        |
| alert\_level   | 1（紧急，由 AlertRuleDefinition.level 定义）                 |
| alert\_message | "温度 触发规则，当前值 85.6℃，阈值 > 80℃"（由 buildAlertMessage 生成） |
| is\_handled    | 0（未处理）                                               |

### 关键技术点解析

- **配置化规则**：规则存储在 `alert_rule_config` JSON 字段中，通过 API 即可修改阈值，无需改代码重新部署
- **设备级优先降级**：设备自身有配置则用设备的，否则降级到设备类型的默认配置
- **指标匹配**：`isMetricMatched()` 确保只有指标匹配的规则才会被评估，避免误触发
- **防重机制**：`getActiveAlertMap()` 一次性获取活跃告警快照，避免 N+1 查询问题
- **消息模板化**：`buildAlertMessage()` 从 `DictMetricService` 缓存获取中文指标名和单位，支持降级策略

## 案例二：批量处理告警记录

### 问题描述

运维人员张三登录系统后，发现有多条未处理告警。他需要一次性处理所有紧急告警（ID为1、3、5），将状态标记为"已处理"并记录处理人和处理时间。

> **⚠️ 校准说明**：当前版本尚未实现独立的 AlertController，告警批量处理需通过 `AlertService.batchHandle()` 直接调用。以下展示的是 Service 层的调用方式，后续可封装为 REST 接口。

### 分步骤解决方案

**步骤1：查询未处理的告警（通过 Service 层）**

```java
List<Alert> unhandled = alertService.findUnhandled();
// 过滤出紧急告警
List<Integer> urgentIds = unhandled.stream()
        .filter(a -> a.getAlertLevel() == 1)
        .map(Alert::getId)
        .toList();
```

**步骤2：批量处理告警**

```java
int handledCount = alertService.batchHandle(
        List.of(1, 3, 5), "张三");
// 返回实际处理的数量（跳过已处理的）
```

**步骤3：Service 层执行批量处理**

```java
@Transactional(rollbackFor = Exception.class)
@Override
public int batchHandle(List<Integer> ids, String handleUser) {
    LambdaUpdateWrapper<Alert> wrapper = new LambdaUpdateWrapper<>();
    wrapper.in(Alert::getId, ids)
           .eq(Alert::getIsHandled, 0)
           .set(Alert::getIsHandled, 1)
           .set(Alert::getHandleTime, LocalDateTime.now())
           .set(Alert::getHandleUser, handleUser);
    return Math.toIntExact(baseMapper.update(null, wrapper));
}
```

**步骤4：验证处理结果**

```java
List<Alert> remaining = alertService.findUnhandled();
// 未处理告警数量应减少
```

### 关键技术点解析

- **幂等性**：已处理的告警不会被重复处理（`alert.getIsHandled() == 0` 判断），即使多次调用也安全
- **事务原子性**：三条告警要么全部处理成功，要么全部回滚
- **防御性编程**：`alert != null` 检查防止传入不存在的告警ID导致空指针异常
- **返回值设计**：返回实际处理的数量，让调用方知道有多少条被跳过

> **💡 面试拓展**：如果批量处理1000条告警，逐条 `getById + updateById` 效率很低。优化方案：
>
> ```sql
> UPDATE alerts SET is_handled = 1, handle_time = NOW(), handle_user = '张三'
> WHERE id IN (1, 3, 5) AND is_handled = 0
> ```
>
> 一条 SQL 完成批量更新，性能提升数十倍。MyBatis-Plus 中可用 `update()` + `LambdaUpdateWrapper` 实现。

## 案例三：定时检测设备离线并自动告警

### 问题描述

系统需要每5分钟自动检查所有在线设备，如果某台设备超过30分钟未上报数据（lastOnlineTime 距当前时间超过30分钟），则自动创建"设备离线"告警。需要避免对同一台设备的同一问题重复创建告警。

### 分步骤解决方案

**步骤1：定时任务触发**

```java
@Scheduled(fixedRate = 300000)  // 每5分钟执行
public void checkDeviceOnlineStatus() {
    log.info("开始检查设备在线状态...");
    // ...
}
```

**步骤2：查询可能离线的设备**

```java
LocalDateTime threshold = LocalDateTime.now().minusMinutes(30);

LambdaQueryWrapper<Device> wrapper = new LambdaQueryWrapper<>();
wrapper.eq(Device::getStatus, 1)           // 状态为在线
       .lt(Device::getLastOnlineTime, threshold);  // 但超过30分钟未上线

List<Device> offlineDevices = deviceService.list(wrapper);
```

**步骤3：检查是否已存在未处理告警（去重）**

```java
boolean alreadyAlerted = alertService.count(
        new LambdaQueryWrapper<Alert>()
                .eq(Alert::getDeviceId, device.getId())
                .eq(Alert::getAlertType, "设备离线")
                .eq(Alert::getIsHandled, 0)
) > 0;
```

**步骤4：创建告警记录**

```java
if (!alreadyAlerted) {
    Alert alert = new Alert();
    alert.setDeviceId(device.getId());
    alert.setAlertType("设备离线");
    alert.setAlertLevel(2);
    alert.setAlertMessage("设备 [" + device.getDeviceName() +
            "] 已超过30分钟未上报数据，可能已离线");
    alert.setIsHandled(0);
    alertService.save(alert);
}
```

### 关键技术点解析

- **去重机制**：通过查询是否已存在同类型未处理告警，避免重复创建。这是**告警抑制**的简单实现
- **时间窗口**：使用 `LocalDateTime.now().minusMinutes(30)` 计算阈值时间点
- **条件组合**：`eq(Device::getStatus, 1).lt(Device::getLastOnlineTime, threshold)` 组合条件精确筛选
- **日志记录**：使用 `log.info/warn` 记录任务执行情况，便于排查问题

> **💡 面试拓展——告警抑制的进阶方案**：
>
> | 抑制策略   | 说明            | 实现方式                |
> | ------ | ------------- | ------------------- |
> | 时间窗口抑制 | 同一设备5分钟内不重复告警 | Redis 设置 key 过期时间   |
> | 告警合并   | 同类型告警合并为一条    | 数据库 GROUP BY + 批量展示 |
> | 告警升级   | 未处理告警自动提升级别   | 定时任务检查未处理时长         |
> | 告警静默   | 维护期间暂停告警      | 配置静默期 + 规则判断        |

| --------------- | ------------- | ----------- |
| `REQUIRED`（默认）  | 有事务加入，无则新建    | 大多数场景       |
| `REQUIRES_NEW`  | 总是新建事务，挂起当前事务 | 独立事务（如日志记录） |
| `SUPPORTS`      | 有事务加入，无则非事务执行 | 查询方法        |
| `NOT_SUPPORTED` | 非事务执行，挂起当前事务  | 不需要事务的操作    |
| `MANDATORY`     | 必须在事务中，否则抛异常  | 被其他事务方法调用   |
| `NEVER`         | 不能在事务中，否则抛异常  | 不需要事务的操作    |
| `NESTED`        | 嵌套事务（保存点）     | 子事务独立回滚     |

#### BUG-F001 | 批量上报未触发告警检测

| 属性        | 内容                                 |
| --------- | ---------------------------------- |
| **缺陷ID**  | BUG-F001                           |
| **类型**    | 功能缺陷                               |
| **严重程度**  | **Critical**                       |
| **受影响模块** | DeviceDataController.reportBatch() |

**缺陷描述**：

- **预期行为**：批量上报数据时，每条数据都应经过告警规则引擎检测，超阈值自动创建告警
- **实际行为**：`reportBatch()` 仅调用 `deviceDataService.saveBatch(dataList)`，完全跳过了 `saveWithAlertCheck()` 中的告警检测逻辑
- **影响**：通过批量接口上报的异常数据不会产生告警，导致监控盲区

**复现步骤**：

1. 通过 `POST /api/device-data/batch` 上报一条温度85.6℃的数据
2. 检查 `alerts` 表
3. 发现无告警记录产生

**修复方案**：

```java
@PostMapping("/batch")
public Result<Void> reportBatch(@Valid @RequestBody DeviceDataBatchDTO batchDTO) {
    List<DeviceData> dataList = batchDTO.getDataList();
    for (DeviceData data : dataList) {
        deviceDataService.saveWithAlertCheck(data);
    }
    return Result.success();
}
```

> **⚠️ 注意**：修复后批量上报改为逐条调用 `saveWithAlertCheck()`，每条数据独立事务。如果需要批量上报的原子性（全部成功或全部失败），应在外层方法添加 `@Transactional`。但需权衡：大批量时事务过长可能导致锁等待。

#### PERF-P002 | DeviceMonitorTask N+1查询问题

| 属性        | 内容                                          |
| --------- | ------------------------------------------- |
| **缺陷ID**  | PERF-P002                                   |
| **类型**    | 性能问题                                        |
| **严重程度**  | **Medium**                                  |
| **受影响模块** | DeviceMonitorTask.checkDeviceOnlineStatus() |

**缺陷描述**：

- **预期行为**：批量检查离线设备时，应避免N+1查询
- **实际行为**：先查出所有离线设备（1次查询），然后对每台设备检查是否已有告警（N次查询）
- **影响**：100台离线设备需要101次数据库查询

**修复方案**：

```java
@Scheduled(fixedRate = 300000)
public void checkDeviceOnlineStatus() {
    LocalDateTime threshold = LocalDateTime.now().minusMinutes(30);

    List<Device> offlineDevices = deviceService.list(
            new LambdaQueryWrapper<Device>()
                    .eq(Device::getStatus, 1)
                    .lt(Device::getLastOnlineTime, threshold));

    if (offlineDevices.isEmpty()) {
        return;
    }

    List<Integer> deviceIds = offlineDevices.stream()
            .map(Device::getId).toList();

    Set<Integer> alreadyAlertedIds = alertService.list(
            new LambdaQueryWrapper<Alert>()
                    .in(Alert::getDeviceId, deviceIds)
                    .eq(Alert::getAlertType, "设备离线")
                    .eq(Alert::getIsHandled, 0)
    ).stream().map(Alert::getDeviceId).collect(Collectors.toSet());

    for (Device device : offlineDevices) {
        if (!alreadyAlertedIds.contains(device.getId())) {
            // 创建告警...
        }
    }
}
```

> 优化后：2次查询（1次查设备 + 1次查已有告警）替代 N+1 次查询。

**修复状态**：✅ 已修复

#### PERF-P003 | batchHandle 逐条更新效率低

| 属性        | 内容                             |
| --------- | ------------------------------ |
| **缺陷ID**  | PERF-P003                      |
| **类型**    | 性能问题                           |
| **严重程度**  | **Medium**                     |
| **受影响模块** | AlertServiceImpl.batchHandle() |

**缺陷描述**：

- **预期行为**：批量处理应使用一条SQL完成
- **实际行为**：逐条 `getById + updateById`，100条告警需要200次数据库交互
- **影响**：大批量处理时性能极差

**修复方案**：

```java
@Transactional(rollbackFor = Exception.class)
@Override
public int batchHandle(List<Integer> ids, String handleUser) {
    LambdaUpdateWrapper<Alert> wrapper = new LambdaUpdateWrapper<>();
    wrapper.in(Alert::getId, ids)
           .eq(Alert::getIsHandled, 0)
           .set(Alert::getIsHandled, 1)
           .set(Alert::getHandleTime, LocalDateTime.now())
           .set(Alert::getHandleUser, handleUser);
    return Math.toIntExact(baseMapper.update(null, wrapper));
}
```

> 一条 SQL 完成批量更新，性能提升数十倍。但注意：此方案不返回每条记录的更新状态，适用于不需要细粒度反馈的场景。

**修复状态**：✅ 已修复

#### PERF-P007 | AlertRuleEngine 告警无去重机制

| 属性        | 内容                            |
| --------- | ----------------------------- |
| **缺陷ID**  | PERF-P007                     |
| **类型**    | 功能缺陷                          |
| **严重程度**  | **Critical**                  |
| **受影响模块** | AlertRuleEngine.createAlert() |

**缺陷描述**：

- **预期行为**：同一设备的同类型告警在短时间内不应重复创建
- **实际行为**：设备持续上报超阈值数据时，每次上报都会创建新告警
- **影响**：温度传感器每秒上报一次，持续超温1小时将产生3600条重复告警——**告警风暴**

**复现步骤**：

1. 温度传感器每秒上报一次85.6℃
2. 持续1小时
3. `alerts` 表新增3600条"高温告警"

**修复方案**：

```java
private void createAlert(Integer deviceId, String alertType,
                         int alertLevel, String alertMessage) {
    boolean alreadyExists = alertService.count(
            new LambdaQueryWrapper<Alert>()
                    .eq(Alert::getDeviceId, deviceId)
                    .eq(Alert::getAlertType, alertType)
                    .eq(Alert::getIsHandled, 0)
    ) > 0;

    if (alreadyExists) {
        log.debug("告警已存在，跳过创建：deviceId={}, type={}", deviceId, alertType);
        return;
    }

    Alert alert = new Alert();
    alert.setDeviceId(deviceId);
    alert.setAlertType(alertType);
    alert.setAlertLevel(alertLevel);
    alert.setAlertMessage(alertMessage);
    alert.setIsHandled(0);
    alertService.save(alert);
    log.warn("告警已触发：deviceId={}, type={}, level={}, msg={}",
            deviceId, alertType, alertLevel, alertMessage);
}
```

**修复状态**：✅ 已修复

将告警检测改为异步处理：

```java
@Transactional(rollbackFor = Exception.class)
@Override
public void saveWithAlertCheck(DeviceData deviceData) {
    Device device = deviceService.getDeviceOrThrow(deviceData.getDeviceId());
    if (deviceData.getCollectTime() == null) {
        deviceData.setCollectTime(LocalDateTime.now());
    }
    deviceData.setCreateTime(LocalDateTime.now());
    save(deviceData);
    
    applicationContext.publishEvent(
            new DataReportEvent(this, deviceData.getDeviceId(),
                    device.getTypeId(), deviceData));
}

@Component
public class AlertCheckListener {
    @Async
    @EventListener
    @Transactional(rollbackFor = Exception.class)
    public void onDataReport(DataReportEvent event) {
        alertRuleEngine.evaluate(event.getDeviceId(),
                event.getTypeId(), event.getDeviceData());
    }
}
```

> **权衡**：异步方案提高了吞吐量，但牺牲了强一致性（数据已保存但告警可能延迟创建）。对于物联网场景，最终一致性通常可接受。

**修复状态**：⏳ 待评估（当前阶段保持同步事务，高并发场景再改为异步）

#### NEW-001 | Integer 拆箱导致 NullPointerException

| 属性        | 内容                                                           |
| --------- | ------------------------------------------------------------ |
| **缺陷ID**  | NEW-001                                                      |
| **类型**    | 功能缺陷                                                         |
| **严重程度**  | **Critical**                                                 |
| **受影响模块** | AlertController.handleAlert()、AlertServiceImpl.batchHandle() |

**缺陷描述**：

- **预期行为**：`isHandled` 字段为 null 时应安全处理
- **实际行为**：`alert.getIsHandled() == 1` 中，如果 `isHandled` 为 null，Integer 自动拆箱将抛出 `NullPointerException`
- **影响**：如果数据库中存在 `is_handled IS NULL` 的记录，处理告警接口将返回500错误

**复现步骤**：

1. 在数据库中手动插入一条 `is_handled = NULL` 的告警记录
2. 调用 `PUT /api/alerts/{id}/handle`
3. 服务端抛出 `NullPointerException`

**修复方案**：

```java
if (alert.getIsHandled() != null && alert.getIsHandled() == 1) {
    return Result.error(400, "该告警已处理，无需重复操作");
}
```

> **💡 面试考点**：Integer 与 int 的拆箱NPE是Java面试经典问题。`Integer == int` 时，Integer 会自动拆箱为 int，如果 Integer 为 null 则抛出 NPE。**防御性写法**：常量放左边 `1 == alert.getIsHandled()` 或先做 null 判断。

**修复状态**：✅ 已修复（AlertController.handleAlert 已更新，AlertServiceImpl.batchHandle 使用 LambdaUpdateWrapper 已规避）

#### NEW-002 | SQL 别名与 Java Map key 不匹配

| 属性        | 内容                                                     |
| --------- | ------------------------------------------------------ |
| **缺陷ID**  | NEW-002                                                |
| **类型**    | 功能缺陷                                                   |
| **严重程度**  | **High**                                               |
| **受影响模块** | DeviceDataMapper.getStatisticsByDeviceIdAndTimeRange() |

**缺陷描述**：

- **预期行为**：SQL 查询返回的 Map key 应与 Java 代码中引用的 key 一致
- **实际行为**：SQL 使用 `AS min_val`（下划线风格），但 Java `getStatistics()` 中使用 `stats.put("minVal", null)`（驼峰风格）
- **影响**：MySQL 默认返回列名为原始别名 `min_val`，Java 代码用 `minVal` 取值返回 null

**修复方案**：已将 SQL 别名从 `min_val/max_val/avg_val` 改为 `minVal/maxVal/avgVal`，与 Java 驼峰命名一致。

> **⚠️ 注意**：如果 MySQL 配置了 `mapUnderscoreToCamelCase=true`（MyBatis-Plus 默认开启），则 `min_val` 会自动映射为 `minVal`。但 `@Select` 注解的原始 SQL 返回 `Map<String, Object>` 时**不经过**此映射，key 保留原始列名。这是 MyBatis-Plus 初学者常见的踩坑点。

**修复状态**：✅ 已修复

#### NEW-005 | AlertRuleEngine 去重存在竞态条件

| 属性        | 内容                            |
| --------- | ----------------------------- |
| **缺陷ID**  | NEW-005                       |
| **类型**    | 安全/并发缺陷                       |
| **严重程度**  | **Medium**                    |
| **受影响模块** | AlertRuleEngine.createAlert() |

**缺陷描述**：

- **预期行为**：同一设备的同类型告警只创建一条
- **实际行为**：`count > 0` 检查与 `save` 之间存在时间窗口，高并发下两个线程可能同时通过检查，各创建一条告警
- **影响**：极端并发场景下仍可能产生重复告警（概率低但存在）

**修复方案**：

方案一（推荐）：数据库唯一约束

```sql
ALTER TABLE alerts ADD UNIQUE INDEX uk_device_type_unhandled 
(device_id, alert_type, is_handled);
```

当并发插入时，第二个事务会因唯一约束冲突失败，由全局异常处理器捕获并忽略。

方案二：分布式锁（Redis）

```java
String lockKey = "alert:" + deviceId + ":" + alertType;
if (!redisTemplate.opsForValue().setIfAbsent(lockKey, "1", Duration.ofMinutes(5))) {
    return;
}
```

> **💡 面试考点**："检查-然后-操作"（check-then-act）是典型的竞态条件模式。解决方案：① 数据库约束（最可靠）② 分布式锁 ③ 乐观锁 ④ 原子操作（CAS）

**修复状态**：⏳ 建议添加数据库唯一约束（Medium级别，当前阶段可接受）

```java
@GetMapping
public Result<Page<Alert>> list(
        @RequestParam(defaultValue = "1") Integer current,
        @RequestParam(defaultValue = "20") Integer size) {
    Page<Alert> page = new Page<>(current, size);
    LambdaQueryWrapper<Alert> wrapper = new LambdaQueryWrapper<>();

    return Result.success(alertService.page(page, wrapper));

@GetMapping("/unhandled")

        @RequestParam(defaultValue = "20") Integer size) {

    LambdaQueryWrapper<Alert> wrapper = new LambdaQueryWrapper<>();
    wrapper.eq(Alert::getIsHandled, 0)

    return Result.success(alertService.page(page, wrapper));
```
