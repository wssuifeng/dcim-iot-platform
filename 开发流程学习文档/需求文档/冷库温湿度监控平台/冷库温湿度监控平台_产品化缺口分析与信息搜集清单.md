# 冷库温湿度监控平台 — 产品化缺口分析与信息搜集清单

> 日期：2026-06-25  
> 阶段：产品化优化计划阶段  
> 目标：把通用 IoT-Platform 收敛为可演示、可讲述、可用于暑假实习/兼职求职的冷链温湿度监控产品案例。

---

## 一、当前判断

冷库温湿度监控是适合当前项目的产品化方向。现有项目已经具备设备管理、数据采集、告警引擎、Redis 缓存、RBAC、审计、通知日志、Excel 导入导出和 Vue 后台，这些能力足以支撑一个垂直场景 Demo。

当前最需要补齐的不是继续堆通用功能，而是把项目讲清楚：

- 面向谁：小型生鲜店、餐饮店、药店、冷链小微运营者。
- 解决什么：远程看温湿度、超限及时发现、历史追溯、报告导出。
- 为什么可信：使用 MQTT 协议接入，模拟设备持续上报，告警和报告能闭环。
- 为什么适合求职：覆盖 Java 后端、前端可视化、消息协议、缓存、部署和压测。

## 二、已发现并修复的文档问题

| 问题 | 影响 | 修复方向 |
|------|------|----------|
| MQTT Topic 一处写 `coldmonitor`，一处写 `coldstorage` | 后端订阅、模拟脚本、接口文档会不一致 | 统一为 `coldmonitor/{deviceCode}/data` |
| 指标编码一处写 `cold_temp/cold_humidity`，一处写 `TEMP/HUMI` | 告警规则无法稳定匹配 `device_data.metric` | 统一为 `cold_temp`、`cold_humidity` |
| 文档引用 `alert_rules` 表 | 当前代码没有该表，规则在 JSON 字段里 | 统一写入 `device_types.alert_rule_config` / `devices.alert_rule_config` |
| 规则运算符写 `>`、`<` | 当前 DTO 只支持 `GT/LT/GTE/LTE/EQ` | 文档改为现有枚举 |
| 设备级规则验收标准逻辑错误 | 9℃ 超过 8℃却写成不触发 | 修正为触发设备级规则告警 |
| PDF、电话、微信、扫码添加过早进入 MVP | 容易拉大范围，影响 8 天交付 | 改为后续增强或预留能力 |

## 三、产品化计划仍缺失的内容

### 3.1 市场与岗位定位缺口

当前文档有“目标用户”和“面试故事”，但缺少更具体的定位证据。

需要补充：

- 目标岗位画像：Java 后端、全栈开发、IoT/工业互联网、企业管理系统、数据可视化后台。

- 兼职/接单边界：这个项目适合作为 Demo、模板化后台、监控大屏外包雏形；不应宣传成可直接用于药品冷链合规生产系统。
- 竞品/替代方案对比：工业动环平台、单机温度记录仪、云组态/IoT 平台、开源物联网平台。

### 3.2 MVP 边界缺口

建议 MVP 只保留：

- 数据入库并触发现有告警。

暂缓：

- 电话/微信通知。
- PDF 报告。

### 3.3 技术设计缺口

需求文档说明了功能，但缺少可直接指导编码的技术设计。

需要补充：

- 大屏接口的数据来源：最新值、24h 趋势、告警列表、统计卡片分别从哪些 Mapper/Service 来。
- Redis 缓存策略：大屏聚合缓存 key、TTL、防击穿方式、失效时机。
- 告警扩展边界：当前规则引擎已有去重/升级能力，超温持续时长、自动恢复、化霜延时是否本期实现。
- 数据保留策略：90 天历史数据是文档目标，但当前是否已有清理任务需要确认。

## 七、当前最重要的取舍

为了暑假求职和兼职收益，优先级应是：

1. 先做能演示的闭环，不先做复杂合规。
2. 先把 MQTT、大屏、告警、报告跑通，不先做多租户。
3. 先用模拟设备讲真实数据流，不急着买硬件。
4. 先补部署和 README，不只停留在本机开发。
5. 先积累压测和截图证据，不只写“熟悉 Redis/Spring Boot”。

一句话结论：这个方向可以继续，但要把它从“学习项目文档”升级成“可交付产品案例文档”。文档的重点要从功能罗列转向范围控制、技术契约、演示路径和岗位映射。
