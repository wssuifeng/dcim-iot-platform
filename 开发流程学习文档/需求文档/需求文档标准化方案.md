## 1. 方案概述

### 1.1 目的

本方案为 IoT-Platform 个人学习项目建立统一的需求文档标准，确保：

- 需求描述无歧义、可验证、可追踪
- 文档结构清晰，便于查阅和迭代
- 从学习项目到生产级实现的差距可量化、可执行
- 支持后续需求持续扩展与维护

### 1.2 适用范围

适用于 `d:\code\iot-platform\开发流程学习文档\需求文档\` 目录下的所有需求文档编写工作。

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| 需求规格说明书 | 描述系统应实现的功能与非功能需求的正式文档 |
| 功能需求 | 描述系统应实现的具体功能行为 |
| 非功能需求 | 描述系统的质量属性（性能、安全、可用性等） |
| 约束条件 | 限制技术选型或实现方式的外部条件 |
| 接口需求 | 系统内部模块间及与外部系统的交互规范 |
| P0-P3 | 需求优先级分级，P0最高，P3最低 |

## 3. 文档标题与版本控制规范

### 3.1 格式标准（元数据块式）

文档开头必须包含以下元数据块：

```markdown
# [项目名称] [文档类型]

> **版本**: V[主版本].[次版本].[修订号] | **状态**: [状态标识]
>
> **创建**: YYYY-MM-DD | **修改**: YYYY-MM-DD
>
> **负责人**: [姓名] ([联系方式])
```

### 3.2 版本号规则

采用三段式版本号 `V主版本.次版本.修订号`：

| 版本段 | 含义 | 变更时机 | 示例 |
|--------|------|----------|------|
| 主版本 | 重大架构变更或需求方向调整 | 需求范围发生根本性变化 | V1 → V2 |
| 次版本 | 新增功能模块或需求章节 | 新增一个模块的需求 | V1.0 → V1.1 |
| 修订号 | 需求细节修正或错误修复 | 修正需求描述歧义 | V1.0.0 → V1.0.1 |

### 3.3 状态标识

| 状态 | 标识 | 含义 |
|------|------|------|
| 草稿 | 🟡 草稿 | 正在编写中，内容可能大幅变动 |
| 评审中 | 🟠 评审中 | 已提交评审，等待确认 |
| 已批准 | 🟢 已批准 | 评审通过，可作为开发依据 |
| 已废弃 | 🔴 已废弃 | 不再使用，已被新版本替代 |

## 4. 需求分类标准

### 4.1 功能需求（FR - Functional Requirement）

描述系统应实现的具体功能行为，回答"系统做什么"。

**识别标准**：
- 有明确的输入和输出
- 可通过操作验证
- 描述的是系统行为而非质量属性

**示例**：用户通过用户名密码登录系统，系统验证后签发JWT Token

### 4.2 非功能需求（NFR - Non-Functional Requirement）

描述系统的质量属性约束，回答"系统做到什么程度"。

| 子类 | 标识 | 关注点 |
|------|------|--------|
| 性能需求 | NFR-PERF | 响应时间、吞吐量、并发能力 |
| 安全性需求 | NFR-SEC | 认证授权、数据加密、防攻击 |
| 可用性需求 | NFR-USAB | 操作便捷性、错误提示友好性 |
| 兼容性需求 | NFR-COMP | 浏览器、操作系统、设备兼容 |
| 可维护性需求 | NFR-MAINT | 代码可读性、文档完整性、可扩展性 |

### 4.3 约束条件（CON - Constraint）

限制技术选型或实现方式的外部条件，回答"系统不能做什么"或"必须用什么"。

| 子类 | 标识 | 关注点 |
|------|------|--------|
| 技术选型约束 | CON-TECH | 框架、语言、数据库版本限制 |
| 开发环境约束 | CON-ENV | JDK版本、操作系统、构建工具 |
| 第三方依赖约束 | CON-DEP | 开源协议、版本兼容性 |

### 4.4 接口需求（INT - Interface）

系统内部模块间及与外部系统的交互规范。

| 子类 | 标识 | 关注点 |
|------|------|--------|
| 内部模块接口 | INT-INT | 模块间调用协议、数据格式 |
| 外部系统接口 | INT-EXT | 第三方API、数据库协议 |

## 6. 需求优先级标识规范

### 6.1 P0-P3分级标准

| 级别 | 标识 | 含义 | 判断依据 | 示例 |
|:----:|:----:|------|----------|------|
| P0 | 🔴 P0-核心 | 不实现则系统无法运行 | 阻断核心业务流程，无替代方案 | 用户认证、设备数据上报 |
| P1 | 🟡 P1-重要 | 影响主要业务流程 | 核心流程缺少该功能会严重降级 | 告警推送、批量操作 |
| P2 | 🔵 P2-一般 | 不影响核心但提升体验 | 有替代方案但效率低 | 数据导出、高级筛选 |
| P3 | ⚪ P3-优化 | 可延后实现 | 锦上添花，无替代方案也可接受 | 设备分组、主题切换 |

### 6.2 优先级判断流程

```
需求是否阻断核心业务流程？
  ├── 是 → P0
  └── 否 → 是否影响主要业务流程？
              ├── 是 → 是否有替代方案？
              │         ├── 否 → P1
              │         └── 是 → P2
              └── 否 → 是否提升用户体验？
                        ├── 是 → P2
                        └── 否 → P3
```

### 6.3 优先级调整规则

- 优先级一经确定，变更需在变更记录中注明原因
- 多个P0需求存在依赖时，被依赖方优先实现
- 迭代规划时，每个迭代至少包含1个P0需求
- P3需求累计超过10个时，需重新评估是否有必要实现

## 7. 验收标准规范（场景用例式）

### 7.1 格式标准

采用 Given-When-Then 行为驱动格式：

```markdown
#### [需求ID] 验收标准

**场景1：[场景名称]**
- **Given** [前置条件描述]
- **When** [触发操作描述]
- **Then** [预期结果描述]
- **通过条件**：[明确判断需求是否通过的具体指标]

**场景2：[场景名称]**
- **Given** [前置条件描述]
- **When** [触发操作描述]
- **Then** [预期结果描述]
- **通过条件**：[明确判断需求是否通过的具体指标]
```

### 7.2 场景覆盖要求

每个功能需求至少包含以下场景类型：

| 场景类型 | 必须包含 | 说明 |
|----------|:--------:|------|
| 正常流程 | ✅ | 主业务路径，输入合法数据 |
| 异常流程 | ✅ | 输入非法数据或异常状态 |
| 边界条件 | ✅ | 空值、极值、临界值 |
| 并发场景 | 视需求 | 多用户同时操作 |
| 性能场景 | 视需求 | 大数据量或高并发 |

### 7.3 验证方法标识

| 方法 | 标识 | 适用场景 |
|------|:----:|----------|
| 手动测试 | 🖐️ 手动 | UI交互、流程验证 |
| 自动化测试 | 🤖 自动 | API接口、回归测试 |
| 代码审查 | 👁️ 审查 | 代码规范、安全检查 |
| 性能测试 | ⚡ 性能 | 响应时间、并发能力 |

## 10. 实施步骤

### 10.1 阶段规划

| 阶段 | 活动 | 交付物 | 时间 |
|------|------|--------|------|
| **方案制定** | 确定标准化方案、选择样式组合 | 本文档 | 第1天 |
| **模板创建** | 基于方案创建需求文档骨架 | 需求规格说明书模板 | 第2天 |
| **需求编写** | 按模块逐个编写需求描述 | 完整需求规格说明书 | 第3-7天 |
| **评审优化** | 自审需求完整性和一致性 | 评审通过的需求文档 | 第8天 |

### 10.2 编写顺序建议

1. 先写P0需求（核心功能），再写P1、P2、P3
2. 先写功能需求，再写非功能需求
3. 每个模块内按依赖关系排序（被依赖方在前）
4. 验收标准与需求描述同步编写

### 10.3 质量检查清单

| 检查项 | 通过标准 |
|--------|----------|
| 需求ID唯一性 | 全文无重复ID |
| 优先级一致性 | 同一需求在不同位置出现时优先级一致 |
| 关联需求有效性 | 所有关联需求ID均存在 |
| 验收场景完整性 | 每个功能需求至少有正常+异常场景 |
| 量化指标明确性 | 非功能需求均有可量化的目标值 |
| 术语一致性 | 同一概念全文使用相同术语 |

## 11. 模板填写示例

### 11.1 功能需求填写示例

```markdown
### REQ-SEC-FR-001：用户JWT认证登录

**📍 基本信息**
- **ID**: REQ-SEC-FR-001 | **模块**: 安全模块 | **优先级**: 🔴 P0-核心 | **类型**: 功能需求

**📝 需求描述**
> 用户通过用户名和密码登录系统，服务端验证通过后签发JWT Token，
> 后续请求在Header中携带Token访问受保护资源，服务端通过Filter验证Token有效性。

**⚙️ 执行条件**
- **前置条件**：
  1. 用户已完成注册且账号状态正常（status=1）
  2. 数据库中存在users表及对应数据
- **后置条件**：
  1. 服务端返回有效JWT Token（有效期2小时）
  2. 登录成功记录写入audit_log表
  3. 用户连续失败计数重置为0

**📋 业务规则**
1. 连续5次登录失败锁定账号30分钟
2. 密码错误提示统一为"用户名或密码错误"，不区分具体原因
3. Token过期后需重新登录，当前版本不支持自动刷新
4. 密码必须使用BCrypt加密存储

**🔗 关联需求**：REQ-SEC-FR-002（Token校验拦截）、REQ-SEC-FR-003（用户注册）、REQ-OPS-FR-001（操作审计日志）
```

### 11.2 验收标准填写示例

```markdown
#### REQ-SEC-FR-001 验收标准

**场景1：正常登录**
- **Given** 用户`admin`已注册且状态正常
- **When** POST `/api/auth/login` 传入 `{"username":"admin","password":"Admin@123"}`
- **Then** 返回HTTP 200，响应体 `{"code":200,"data":{"token":"eyJhbG..."}}`
- **通过条件**：Token可成功解码且包含`sub`、`exp`字段，有效期=2小时

**场景2：密码错误**
- **Given** 用户`admin`已注册
- **When** POST `/api/auth/login` 传入 `{"username":"admin","password":"wrong"}`
- **Then** 返回HTTP 401，响应体 `{"code":401,"message":"用户名或密码错误"}`
- **通过条件**：错误提示不区分"用户名不存在"和"密码错误"

**场景3：账号锁定**
- **Given** 用户`admin`连续5次登录失败
- **When** 第6次POST `/api/auth/login`
- **Then** 返回HTTP 403，响应体 `{"code":403,"message":"账号已锁定，请30分钟后重试"}`
- **通过条件**：锁定后即使密码正确也返回403，30分钟后自动解锁

**场景4：Token过期访问**
- **Given** 用户持有2小时前签发的Token
- **When** GET `/api/devices` 携带该Token
- **Then** 返回HTTP 401，响应体 `{"code":401,"message":"Token已过期"}`
- **通过条件**：过期Token无法访问任何受保护接口
```
